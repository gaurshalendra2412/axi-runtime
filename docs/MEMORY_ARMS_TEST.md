# Test 44: a chat that must remember the state (kept, summarised, windowed, retrieved) against the exact-state arm, on a 14B model, jobs of 600 steps (written BEFORE the run, 16 Nov 2026)

*The architecture is Rajnish Choubey's; the code and every measurement are the owner's, with an AI assistant as a tool. AXI is a layer on the host side: the host holds the state, the model is unchanged, and every claim here is about the state the host holds. This page is written before the harness is run on the model; the Result goes below it and nothing above the Result line is edited afterwards.*

## Why this test
"Nobody keeps the whole chat: tools summarise it, cut it to a window, or fetch the old turns that matter." That is the fair objection to every kept-chat comparison so far (Tests 19, 21, 35, 38 and 42 keep the whole chat and show the state at every turn). `COMPACTION_TEST.md` put summaries against AXI on a hosted model (Gemini) with a heavy turn at every step. This test puts the four ways a chat is kept short against the exact-state arm on an **open 14B model on one card**, where the prompt, the cache and the seconds can all be read. **The question: when the chat shows the state once and then has to remember it, how often is each step right, how often is the state the host holds the oracle's, and what does a step cost, for a kept chat, a generic summary, a summary that writes the state out, a sliding window and retrieval, against the exact-state arm?**

## What I read before writing this page
Offline, from the repository's job generator (CPU, no model), recorded here so the predictions are read knowing it:
* Jobs 192, 194 and 196 of the sixth run's generator, asked for 600 steps, give 600 steps each. Their requests are about one third each of "add a service" and "add an edge", and **about one fifth are deletes of a service that has edges** (132, 138 and 146 of 600), where the reply must list every edge attached to the service: this is where a chat that has to remember can go wrong. The other deletes (a service with no edge) and the adds need nothing from memory except the numbers the request does not give.
* The grammar that names the coordinates (`named`) fixes the kind of reply and the coordinates the request names; the model still writes the numbers, and for a delete the edges (any edge that touches the service, with any relation and weight). A reply that lists the wrong edges is inside the grammar. So a miss on a delete is a failure of memory, not of format.
* A check of the harness on a test double (no model), made before this page was locked and not a result: when a reply to a delete leaves out an edge, the host's gate and repair (`repair_m6`) complete the delete and the held state stays the oracle's (`exact_policy` 100 %), while the same reply applied with no check leaves the state wrong from then on (`exact_blind` near 0 %). Line 13 was written with that in mind (first draft: 65 % that all four arms are at least 5 points below `A`; changed to the line below before any model run). The test therefore separates AXI's two parts: the exact-state prompt (which makes the model's own step right: `step_ok`) and the host's gate and repair (which hold the state whatever the model's step was: `exact_policy`).
* A lean chat grows about 60 tokens a step (the request, the reply and the chat template), so a chat of 600 steps would pass 36,000 tokens. The Test 42 plan says the repository's whole-chat arm (which shows the state at every turn) grows about ten times faster; the lean chat here is the best case for a kept chat.

## What is run
Model `Qwen/Qwen2.5-14B-Instruct-AWQ` (4-bit), vLLM 0.31.0, one NVIDIA L4, prefix caching on, cache 2,000 blocks (32,000 tokens), `max_model_len` 20,000 (the model's own window is 32,768; 20,000 is what a 2,000-block cache can hold for one sequence with room), greedy decoding, no retry, at most 96 new tokens for a step, the grammar that names the coordinates for every arm, policy `repair_m6` for the host's gate and repair where it is used. Jobs 192, 194 and 196 (the same three jobs in every arm), 600 steps each, three jobs side by side in lockstep rounds. The code is `python/axi/experiments/provider_side_memory.py` (a new file; it edits no earlier file; it uses the harness of Tests 35 to 43 unchanged).

The chat arms are **lean**: the first user message shows the whole state and the first request; every later user message is only the request. The model's own replies stay in the chat. The state is never shown again, except through what a summary keeps.

| arm | what it is |
|---|---|
| `A` | the exact state each step (fresh prompt: system, state the host holds, request), host gate and repair; `provider_side_typed.TypedSession`, unchanged |
| `K` | the lean chat kept whole; a chat stops before its next prompt would pass **16,000 tokens** (the limit is set by this test, under the engine's 20,000) |
| `S` | `K`, and when the next prompt would pass **4,000 tokens** the model is asked for a **generic summary** ("summarise our conversation so far; your summary will replace the conversation, so include everything you will need to carry on the work correctly"); the chat is emptied and the summary leads the next message |
| `V` | the same as `S`, but the model is asked to **write out the complete current list of services and edges** exactly as they stand, in the format of the state, and any rule it has noticed (the rival built by someone who knows the job) |
| `W` | a sliding window: the first turn (which shows the state) is pinned, then only the **last 12 turns** |
| `R` | retrieval: the first turn pinned, the **last 4 turns**, and the **8 earlier turns that share the most coordinates** with the request (counted over the turn's request and reply; ties to the later turn) |

The summary call reuses the chat as its prefix (same system text, the same history, one more user message), so it gets the prefix cache like any other call. The summary is written with no grammar, at most 1,000 tokens. **Every summary is kept in the file with the oracle's state at that step**, so that anyone can read what the model kept, and for `V` (and `S`, if it writes one) the NODES and EDGES lines are compared with the oracle's state.

## What is measured
Per arm and per job: the flags of a step, which are three:
* `step_ok`: the reply, applied with no check to the oracle's state **before** the step, gives the oracle's state after it (the step itself was right; an earlier mistake does not count against it);
* `exact_blind`: the state the host holds if it applies every reply as it comes, with no check, equals the oracle's after the step (what the chat alone gives);
* `exact_policy`: the same with the host's gate and repair (`repair_m6`); for arm `A` this is the exact share of Tests 35 to 43.

Also: replies accepted by the strict parser; steps reached before a stop; `step_ok` on deletes of a service with edges and on the other requests; the first step on which `step_ok` is false, and the first on which `exact_blind` is false, per job; summaries per job, their length, how many reached the 1,000-token limit, and for `V` the share whose written-out state equals the oracle's; prompt tokens a step; **computed** prompt tokens a step (prompt minus cached, **summary calls included**) and the share served from the cache; seconds a step (summary calls included); the GPU board's mean power.

## Predictions (mine, written first)
Each line carries my probability that it reads "yes". A line that comes out "NO" is a finding, not an error. "Over the arm" means over its 3 jobs together (1,800 steps; fewer for `K`).

1. [instrument] every arm ran without an engine error; `A`, `S`, `V`, `W` and `R` ran all 600 steps on every job; the replies were accepted by the strict parser on at least 98 percent of steps in every arm (80 %)
2. [instrument] `S` and `V` each made at least 5 summaries on every job (85 %), and at least 90 percent of the summaries ended before the 1,000-token limit in each of the two arms (80 %)
3. [claim] every kept chat (`K`) ended at its 16,000-token limit before step 400 (90 %): that is the arithmetic of the chat's growth, reported as a fact about the kept chat and not as a saving of the exact-state arm
4. [claim] arm `A`: `step_ok` and `exact_policy` are each at least 99 percent over the arm (85 %)
5. [claim] arm `K`: `step_ok` is at least 99 percent on the steps it ran (55 %)
6. [claim] arm `S`: `step_ok` over the arm is at least 3 points below that of `A` (65 %)
7. [claim] arm `V`: `step_ok` over the arm is at least 3 points below that of `A` (50 %)
8. [claim] arm `W`: `step_ok` over the arm is at least 3 points below that of `A` (85 %)
9. [claim] arm `R`: `step_ok` over the arm is at least 3 points below that of `A` (55 %)
10. [claim] at least one of `S`, `V`, `W` and `R` has a `step_ok` within 1 point of `A`'s over the arm (20 %)
11. [claim] in each of `S`, `V`, `W` and `R`, `step_ok` on deletes of a service with edges is at least 5 points lower than on the other requests (80 %): memory matters where the edges must be listed
12. [claim] `exact_blind` of each of `S`, `V`, `W` and `R` is at least 10 points below `A`'s `exact_policy` (75 %): one wrong step the host applies with no check stays in the state
13. [claim] `exact_policy` of each of `S`, `V`, `W` and `R` is at least 95 percent (60 %): the host's repair completes a delete's missing edges whatever the chat remembered, so the host's gate may hold the state even when the chat's own reply is wrong; and at least one of the four is at least 5 points below `A`'s `exact_policy` (25 %)
14. [claim] `V`: at least 80 percent of its summaries write out a state that equals the oracle's exactly (40 %)
15. [claim] computed prompt tokens a step (summary calls included): `A` is lower than `W` and than `R` (85 %)
16. [claim] computed prompt tokens a step (summary calls included): `A` is lower than `S` (45 %) and `A` is lower than `V` (45 %): an honest coin flip, a summary chat computes few new tokens between summaries
17. [claim] seconds a step (summary calls included): `A` is lower than each of `S`, `V`, `W` and `R` (55 %)
18. [claim] arm `A`: `step_ok` over steps 401 to 600 is within 2 points of that over steps 1 to 200 (80 %), and the mean prompt of the last 100 steps is at most 1.3 times that of the first 100 (90 %)
19. [claim] the share of prompt tokens served from the cache: `K` at least 90 percent (75 %); `W` and `R` each lower than `K` (90 %)

What would count against AXI here: **a memory arm (`S`, `V`, `W` or `R`) whose `step_ok` and whose `exact_policy` are both within 1 point of `A`'s over the arm and which computes no more prompt tokens a step than `A` (summary calls included)**: that arm matches the exact-state arm at no extra cost on this job family and this model. Also: arm `A` below 95 percent `step_ok`. Each is reported as it is. Not counting against AXI and not for it: that the kept chat cannot go on past its 16,000-token limit (line 3); and a summary arm that computes fewer tokens than `A` while being less exact (line 16 may read "NO" without that being a finding against `A`'s exactness: the two things are reported side by side).

## Honest limits
One card (L4), one 14B quantised model, greedy decoding, one engine and its version, synthetic service graphs, three jobs of one family, 600 steps (the longest chat arm holds about 40,000 tokens at the end and so cannot be run whole: `K` stops at 16,000). The prompts of the summary arms are written by me (one generic, one that asks for the state); a better summary prompt, a longer window, a different retrieval rule (embedding search, a graph of services instead of words) or a larger budget would move the numbers of those arms, and a model that was trained for summaries would too. The window (12 turns) and retrieval (4 + 8 turns) sizes are one choice each, fixed before the run. The 2,000-block cache (32,000 tokens) is smaller than three 16,000-token kept chats, so late in `K` the cache is under pressure; seconds of `K` are read with that in mind. `step_ok` is worked out against the oracle's state, so a chat that is wrong once and right afterwards is scored on each step alone, while `exact_blind` carries one mistake forward; both are reported. The host's gate and repair (`exact_policy`) are the same code as in the exact-state arm; they can repair a reply the model got partly wrong, which is the framework working, but they are not a memory. The per-step files stay on the Colab machine; a compact export of the per-step flags and every summary, with the sha256 of each raw file, is saved with the Result. Test 5 of the owner's list is this page; Test 42 is the whole-chat arm at length; the other kinds of state (code patches, tables, scheduling, JSON tool calls) are another page.

**What this says, in plain words, and what it does not.** The host's gate and repair did their job in every arm: the state the host held was the oracle's on all 1,800 steps of `S`, `V`, `W` and `R` (and `A`, and the 1,160 of `K`), although the replies of the chat arms were wrong on 6 to 16 percent of steps, because the gate completes the missing edges of a delete (`exact_policy` 100.0). The same replies applied with no check give a state that is right on 0.4 to 0.7 percent of the steps. That separation is the page's own check, and it holds here. What did **not** hold is the expectation behind arm `A`: showing the exact state at every step did not make the model's own step right more often than a chat that remembers it (81.89 against 84.00 to 93.83), the model listed the right edges of a deleted service on 21.63 percent of the requests (the chat arms on 30.77 to 73.32), and a summary chat computes fewer new tokens than `A`. Arm `A` is the fastest in seconds and the cheapest of the four arms that do not summarise. This test does not show why `A`'s delete is so weak (the model must list every edge of the service in the grammar's free part; the host completes it), and it did not try an arm that asks the model for less (for example, a delete reply that names only the service and leaves the edges to the host); that is a test of its own and not a claim here.
