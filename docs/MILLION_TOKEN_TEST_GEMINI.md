# Million-token test on a current hosted model: 3,600 steps of Gemini 3.5 Flash Lite with the scope filter (written BEFORE the run, 12 Oct 2026)

The question that came after the Qwen page (`docs/MILLION_TOKEN_TEST.md`): "why test it on a small model; can't we test it on a model of today?" This page is the same test with a current hosted model in place of the open one. A model is shown the exact state of a service graph at every step, is asked for one change, and the framework (scope_m7) decides what to keep; this is repeated for 3,600 requests in a row, about 1.4 million tokens, and the held state is compared with the right one at every step. Nothing is stored in a model's context from one step to the next, so what could go wrong is in the held state, in the speed, in the replies the code cannot read, or in the model's own slips; those are what is read.

**What this is and what it is not.** One model: Gemini 3.5 Flash Lite (`gemini-3.5-flash-lite`), Google's small, fast tier. It is a current model; it is **not** a Pro model and not a frontier model, and every sentence about it says "Flash Lite". One task family (graphs of at most 14 services and 26 edges), the stream, the thirteen reading rules and every threshold of the Qwen page, unchanged. What differs from the Qwen page is the model and, with it, three things: the model's replies are **sampled** (the temperature is left at the model's default, as in the earlier Flash Lite tests, so one run is one sample and a repeat would write another history), the output is **not** constrained by a grammar (the model may write anything; the strict parser decides what is read), and a repeated prompt is answered from the saved reply and **not sent again**. The Qwen result is not known to me (that run has not been made); nothing on this page was shaped by it, and the two pages are separate tests that share their stream and rules.

## What is run
* **Run 1 (the test).** One episode, stream seed 20261021, 3,600 requests, policy scope_m7. Each step is one call to the service, unless the identical prompt was already asked and saved (then the saved reply is used and the step is marked `cached` and not counted as sent). The model is shown the policy's own held state, the request is made on the oracle's state. After every step the file on disk holds the step; if the session stops, running the same cell again replays the saved replies through the same stream and policy, checks that every saved flag is reproduced, and carries on (`million.replay`).
* **Contrast.** On the first 300 requests of the same stream, blind apply, the gate and repair_m6, each with its own held state. Where a policy's prompt is the same as one already asked, the saved reply is reused (so the comparison is paired on the same sampled reply wherever the states coincide); fewer than 900 calls are therefore made.
* **Run 2 (optional, for "two million").** The same with stream seed 20261022. Only if there is time or budget; the page says what is read if it is not made.
* **Requests.** `million.LiveStream`, exactly as on the Qwen page: `endurance.Stream` with the kinds {add service x3, add edge x4, delete with dependants x1, delete without x1, delete edge x1, delete service and edge x1}, so that the graph stays at about 10 services and 5 to 10 edges and a service delete that has dependants comes up in about 17 percent of the steps. Measured on the oracle's stream: a delete of a service together with an edge comes up in about 8 to 9 percent of the steps, a delete of a service without dependants in about 9 percent, a delete with dependants in about 9 percent, a delete of an edge in about 8 to 9 percent, an add of an edge in about 38 percent and an add of a service in about 26 percent.
* **Measured at every step.** Prompt tokens, visible reply tokens and **thinking tokens** (the service's own counts), seconds of the one successful call (waiting and retrying are not in it), whether the strict parser accepted the reply, whether the held state is well formed, the distance to the oracle (items that differ), whether the held state equals the oracle's, whether the step started from the oracle's state, whether the requested change could be applied as written to the held state, and if so whether the step did it.
* **Model and settings.** `gemini-3.5-flash-lite` (the notebook looks up the id the key can see and records it in the file; if Google changes what the name points to during the run, that is not visible to it), sampling at the model's default temperature, **thinking at the model's default unless the 20-step check says otherwise** (see below), at most 8,192 output tokens including thinking, no grammar, the same system text and user text as every earlier run, the rule about deleting dependants NOT stated.
* **The 20-step check, and the one decision it can make.** Before run 1 the notebook runs 20 steps of a different stream (seed 99, so nothing of the stream of this page is used) and prints tokens a step, thinking tokens a step, seconds a call and the projected total. **If it shows more than 20 thinking tokens a step, the thinking level is set to "minimal" before run 1** (thinking tokens are billed as output and would change the cost, and the earlier Flash Lite tests did not record them); that is the only setting that may be changed, it is decided before run 1 is started, and the Result says which was used. Otherwise the default stays. No other setting, threshold or line is changed after seeing any output.
* **Free key or paid key, the owner's choice.** On the free tier the notebook allows itself 480 calls a day (AI Studio showed about 500 a day for this model on 9 Oct; the service's own answer is what really stops a run), spaced 4.5 s apart, so run 1 takes about 8 days, one cell run a day, and the contrast a day or two more. With billing turned on by the owner (the notebook never turns it on), there is no daily stop and run 1 takes about an hour. Both give the same file format and are read by the same lines. **No price is assumed on this page:** prices pasted into the chat from another assistant were not verified, and the notebook prints a dollar figure only from two prices typed in from the AI Studio price page. What is fixed is a cap: each run (run 1, each contrast file, run 2) stops by itself once it has sent 2,000,000 tokens (prompt, visible reply and thinking tokens of the calls really made), whatever the price.

## What was seen before this page was written
* **No call was made on the stream of this page.** Only the oracle was: the stream of seeds 20261021 and 20261022 was generated for 3,600 steps to check that it does not end early (it does not) and how big the graph is (services 7.5 to 11.7 and edges 2.7 to 9.8 on average in the ten tenths of the two seeds; at most 14 and 26). The request weights were chosen from 216 candidate weightings (and four tried by hand before) by a search on the oracle's graph size (seed 20261015, 1,500 steps); one met the targets; other seeds were used to check it. The Qwen run has not been made either.
* **Token estimate.** The prompts of this stream, built on the oracle's states, are on average 927 characters (920 for the second seed). The Qwen line (tokens = -256.8 + 0.6709 x characters) gives about 365 prompt tokens and, with a reply of 11 tokens, about 376 a step. The Flash Lite service counted 308.6 prompt tokens a step in the 30-step runs against 307.3 for Qwen on the same step mix, on graphs a little smaller (4.9 services on average against 5.8), so it counts slightly more per character, and its replies were 14.6 tokens against 11.3. My estimate is **380 to 410 visible tokens a step, about 1.4 million for 3,600 steps**, plus thinking tokens, which are unknown because the saved Flash Lite files do not record them. A call time of 0.5 to 0.6 s with a 300-token prompt is hard to square with hundreds of thinking tokens a call.
* **What shaped the probabilities.** The saved Flash Lite tests on the scope mix (`docs/API_TEST_GEMINI.md`, Part A, seed 7, thinking and temperature at the default, no rule stated): 4 episodes of 30 steps, **scope_m7 and repair_m6 held the oracle's state on 120 of 120 steps**, 0 corrupted, 0 unparsed; blind apply held it on 61 of 120 and a corrupted graph on 59, 3 of 4 episodes were corrupted at some step (first at step 3, 13 and 14), all from a delete of a service together with an edge, where the raw model left a dangling edge on 15 of 20 requests; on a delete with dependants it was right 20 of 20 without help (the 7B was right on none). 0.53 to 0.56 s a call. **The replies that cannot be read are the doubt:** 3 of 140 single replies were unparsed with no rule stated (all on deletes: `DEL[r,c:v]`, the id written with a number after it, which the format does not have), 0 of 177 in the long runs; with the rule stated, 75 of 334 replies were unreadable, all the same slip. An unreadable reply changes nothing for any policy, so after an unreadable delete the held state keeps a service the oracle has deleted, and that offset stays until the id is added again; the scope filter cannot see it. That, and not a legal slip, is what I expect to set the distance in this run. No stream of this page has been looked at in any model's replies.

## Predictions (mine, written first; the number is how sure I am)
1. [guard] Run 1 reaches step 3,600 and its replay reproduces every saved flag. (85 %) The doubts are the service (a long run over days or an hour, a busy server, a silent change of the model), the cap, and a problem in the code I have not met; the framework is not the doubt. A run that stops before step 3,600 is reported as stopped at step N, line 1 reads NO, and the other lines printed for it describe the first N steps only.
2. [guard] scope_m7 is never corrupted. (99 %) The gate checks well-formedness on every step.
3. [instrument] The strict parser refuses at most 2 percent of the replies. (80 %) Unreadable replies were 3 of 317 in the no-rule Flash Lite runs, but all on deletes of a service, which are about 18 percent of this stream; the model is not grammar-constrained here, and I expect between a half and one and a half percent.
4. [instrument] Blind apply is corrupted on at least 50 percent of its first 300 steps. (96 %) The raw model left a dangling edge on 15 of 20 deletes of a service with an edge, these are 8 to 9 percent of the steps, and a dangling edge stays.
5. [claim] Run 1 sends at least 1,000,000 tokens. (95 %) My estimate is 1.4 million visible tokens; this fails only if a step costs less than 278.
6. [claim] Mean distance in the last tenth is at most 1.0 above the first tenth's. (85 %) I expect the offset to be a balance between unreadable deletes arriving and ids being added again, so about the same in every tenth.
7. [claim] The distance never exceeds 10 items. (85 %) A burst of unreadable replies (a busy service, empty answers) is the doubt.
8. [claim] At least 80 percent of the steps of the last tenth hold exactly the oracle's state. (35 %) This is the line I am least sure of, and I expect it to fail: one unreadable delete leaves the state off for about as long as it takes the id to be added again (I guess 40 to 100 steps), (the grid has 30 cells and about 20 are free, so a given cell is chosen again once in about 75 steps on average), so exactness at 80 percent needs unreadable deletes rarer than roughly one in 150 to one in 450 steps depending on that time; the saved runs suggest about one in 75 to one in 200 per step.
9. [claim] The share of applicable steps that did not do what was asked is, in the second half, at most 2 points above the first half's. (88 %) Both halves of the same model on the same stream; it fails only if something changes during the run.
10. [claim] Mean prompt tokens in the last tenth are at most 1.5 times the first tenth's. (95 %) The stream itself moves them by about 10 percent from tenth to tenth.
11. [claim] Mean seconds a successful call takes in the last tenth are at most 1.5 times the first tenth's. (65 %) A hosted service's speed moves with its load; on the free route the first and the last tenth are about a week apart.
12. [claim] In steps 201 to 300, scope_m7's mean distance is smaller than blind apply's and than the gate's. (95 %) The gate rejects the raw model's dangling-edge replies and then holds a state that never gets the change.
13. [claim] Only if run 2 is made: it also reaches step 3,600, lines 2, 3 and 6 to 11 also hold for it, and the two runs together sent at least 2,000,000 tokens. (25 %) Seven lines at once, among them line 8.
14. Not reading-rule lines. Tokens sent in run 1 are between 1.2 and 1.8 million (75 %). Thinking tokens a step in the 20-step check are at most 20, so that the default stays (80 %). The mean seconds of a call are between 0.4 and 2.0 (75 %). The share of unreadable replies over the whole run is between 0.2 and 2.0 percent (65 %). The share of steps equal to the oracle over the whole run is between 40 and 90 percent (60 %). The mean distance over the whole run is between 0.2 and 2.0 (65 %). In steps 201 to 300 the mean distance of blind apply is above 10 (80 %) and the gate's above 10 (70 %). Of the steps where the held state first leaves the oracle's (start equal, end not), at least two thirds follow a reply the parser refused (65 %).

Overall: that all twelve lines of run 1 and the contrast (lines 1 to 12) come out "yes" I rate about **15 %** (lines 6 to 9 are one question asked four ways, and lines 3 and 8 depend on the same unreadable replies); that lines 1 to 4, the guard and instrument lines, all do, about **65 %**.

## Reading rules (fixed now; the program prints exactly these)
Thirteen lines, tagged **[guard]**, **[instrument]** or **[claim]**, the same as on the Qwen page. Code: `million.verdict_million`. Each is answered "yes", "NO" or "not run" (lines 4 and 12 need the contrast, line 13 needs run 2).
1. [guard] run 1 reached step 3,600 with every step on file, and the replay of its saved replies reproduces every saved flag of every step
2. [guard] scope_m7 was never corrupted (no edge pointing at a missing service) at any step of run 1
3. [instrument] the strict parser refused at most 2 percent of the replies of run 1
4. [instrument] blind apply, on the same requests, was corrupted on at least 50 percent of its first 300 steps
5. [claim] tokens sent in run 1 (prompt plus reply, counted by the model's own tokenizer) are at least 1,000,000
6. [claim] the mean distance to the oracle in the last tenth of run 1 is at most 1.0 above that of the first tenth
7. [claim] the distance to the oracle never exceeded 10 items at any step of run 1
8. [claim] at least 80 percent of the steps of the last tenth of run 1 hold exactly the oracle's state
9. [claim] among the steps of run 1 that start from the oracle's state and ask for a change that can be applied, the share that did not do what was asked is in the second half at most 2 percentage points above that of the first half
10. [claim] the mean prompt tokens of the last tenth of run 1 are at most 1.5 times those of the first tenth
11. [claim] the mean seconds a step takes in the last tenth of run 1 are at most 1.5 times those of the first tenth
12. [claim] in steps 201 to 300, scope_m7's mean distance to the oracle is smaller than blind apply's and smaller than the gate's, on the same requests
13. [claim] run 2 (the second seed) also reached step 3,600, and lines 2, 3 and 6 to 11 also hold for it, so that the two runs together sent at least 2,000,000 tokens (only if run 2 was made)

**How the result will be worded.** A "NO" on line 1 is looked into before anything else is read: a crash or a replay mismatch is a bug to be fixed in a separate commit, with a test, and the run repeated on a new seed rather than edited; a stop by the service or the cap is reported as a stop. Lines 3 and 4 are about the instrument: if line 3 fails, the distance is read together with the count of unreadable replies, and the cause of every new offset (an unreadable reply, or a readable reply that did the wrong thing) is counted from the saved rows and reported; if line 4 fails, the model did not break the raw state and the layer was not needed on this stream, which is reported as exactly that (it did no harm if lines 2 and 6 to 9 hold) and not as a result for the framework; line 12 then also reads NO and is not a failure. A "NO" on line 2 is a finding about the framework. **A "NO" on lines 6, 7 or 8 is read by its cause.** If the new offsets follow replies the parser refused, the finding is that the scope filter cannot defend against a lost update (a reply that says nothing), and that a step which re-asks on an unreadable reply, or re-checks the held state against something the model did not write, is needed; a retry is a separate test (not built), and it is not claimed here that it would fix it. If they follow readable replies that did the wrong thing, the finding is the one on the Qwen page: legal slips pile up faster than the stream removes them. Either way it is reported as a limit, with the number, not as a failure of the run. A "NO" on line 10 means cost per step grows with the length of the job. A "NO" on line 11 is first compared with the means per day and per tenth and with line 10: on a hosted service, speed changes between days for reasons that are not the job's length, and that is how it will be worded. A "yes" on a line is a statement about this model on this stream and nothing more.

## What this does not show
That a model is accurate "at a million tokens" in the sense of one conversation of a million tokens (the model never sees more than one state and one request); that any other model behaves like this one (a Pro model, another provider's model, a different Flash Lite release); that another task, with state that must grow, would stay flat (this graph is capped at 14 services and 26 edges); that real users' requests look like these (each request names its targets by coordinate and is phrased in the same few ways); that the savings against a chat that keeps its history, or that caches its prefix, are the extension in `docs/ENDURANCE_TEST.md` (they are not measured here: the history side is not run); that a repeat would give the same numbers (replies are sampled; one run is one sample); that a free run spread over about a week and a paid run of an hour are the same thing to the service (the Result says which was made). The comparison of the first and the last tenth compares two stretches of ONE stream, whose graph size moves by itself from tenth to tenth, so a small difference in either direction is not read as a trend. Cost in money is not a result of this page.

## How it is run
`python/colab/axi_million_gemini.ipynb` with `axi-colab-million.zip` on Colab's free CPU runtime (no GPU is needed). The key lives in Colab Secrets and is never printed or saved. Cells 1 to 5 prepare (about a minute), the 20-step check follows, then run 1 (free: about 8 cell runs on as many days, progress shown every 100 steps and saved to Google Drive every 25; paid: about an hour), then the contrast, then run 2 if wanted. If the session stops, or the day's budget is used, run Cells 2 to 5 again and then the same cell: it continues from the last saved step. The files that come back are read here by `python/tests/test_million_gemini_result.py`, which recomputes every number of the Result below from them.
