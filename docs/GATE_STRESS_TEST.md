# Test 39: hostile text, a crash in the middle of a commit, replay and many writers at the front door (written BEFORE the run, 16 Nov 2026)

*The architecture is Rajnish Choubey's; the code and every measurement are the owner's, with an AI assistant as a tool. AXI is a layer on the host side: the host holds the state, the model is unchanged, and every claim here is about the state the host holds. This page is written before the harness exists and before any of its numbers; the Result goes below it and nothing above the Result line is edited afterwards. No model is called, no GPU and no key are used: the test runs on a CPU.*

## Why this test
A safety team that puts a layer between a model and the state it edits asks four plain questions of that layer. What happens when the text it is handed is hostile, not merely wrong? What happens if the machine dies in the middle of a commit? Can the state be rebuilt exactly from a log? What happens when many writers hit it at once? The repository answers parts of these: the endurance test (Part C of `ENDURANCE_TEST.md`) ran about 1.6 million steps with 15 kinds of damaged reply; the swarm test (`SWARM_TEST.md`) ran independence rules, 64-agent rounds and a store shared by eight threads; `tests/test_dist_commit.py` fault-injects 6,000 proposals into five ranks. **What none of them did:** put prompt-injection text and control or look-alike characters through the real front door (`Runtime.propose`: strict parse, page writes, gate, commit); compare it with an independent reference on every proposal; replay a log bit for bit; crash the process inside a commit; or run many threads against one `Runtime`. **The question: at the front door of the Python reference model, 10 million hostile or random proposals in, which guarantees hold and which break?**

## What was seen before this page was written
Three probes, made while reading the code, are recorded here so the predictions below are read knowing them.
* A node coordinate, node value or edge weight written with **5,000 digits** made `Runtime.propose` raise an uncaught `ValueError` ("Exceeds the limit (4300 digits) for integer string conversion"), instead of returning a refusal. A 4,000-digit coordinate was committed. The limit belongs to CPython 3.11 and later (here 3.13.18; it can be switched off by the host program); the parser's docstring says anything outside the grammar "raises CICOParseError", and this is a ValueError. This is a finding already, before the run; the run asks how wide it is.
* Reading `runtime.py`: the page of a service is `row * 65,536 + column`, so `(0, 65536)` and `(1, 0)` have the same page. I have not run this case. A deletion of one would unmap the page of the other.
* Reading `runtime.py` and `gate.py`: a delta that only deletes an edge writes no page, so two such deltas on the same edge do not conflict at the pager. The class is used one proposal at a time (the swarm page says so); I have not run the case with threads.
* Speed, from a 200,000-proposal run of short strings: about 32 microseconds per proposal, which is why 10 million is possible on a CPU.
No other run of this harness has been made.

## What is run
The Python reference model of the repository, unchanged and not edited (`python/axi/engine`: `runtime.py`, `cico_parser.py`, `gate.py`, `pager.py`, `dist_commit.py`, repo commit `55631ec`), CPython 3.13.18 with its default integer-string limit, two cores. The harness is new code, written after this page, in `python/axi/experiments/gate_stress.py`; no file of the framework is changed. A fresh `Runtime(capacity=20000)` is used for each of **100 segments of 100,000 proposals** (10,000,000 in all), with segment seeds fixed in the code (`20261116000` + segment number).

**Part A: hostile and random text, with an independent reference.** Fourteen families of proposals, in the shares given:

| family | what it is | share |
|---|---|---|
| 1 legal | a legal edit built from the live state (add or delete a service, add or delete an edge, small batches); keeps the graph evolving, below about 400 services | 20 % |
| 2 mutated | a legal proposal with bytes flipped, deleted, inserted, swapped, two proposals spliced, or cut | 15 % |
| 3 random bytes | random bytes (0 to 200) decoded with `latin-1`, and random Unicode text | 8 % |
| 4 token soup | random items of the grammar's alphabet joined by random separators | 8 % |
| 5 injection alone | one of about 60 injection strings: instructions to ignore earlier rules, role markers, chat-template tokens, fake `<CICO_STATE>` blocks, tool-call JSON, markdown fences, SQL, shell, format and log-lookup strings | 6 % |
| 6 injection around a legal proposal | a legal proposal with an injection string before it, after it, or both, separated by a space or a newline | 8 % |
| 7 control characters | NUL, tab, carriage return, vertical tab, form feed, zero-width and bidirectional-override characters, byte-order mark, lone surrogates, line and paragraph separators, put into legal proposals | 6 % |
| 8 look-alike digits | full-width, Arabic-Indic, superscript and mathematical digits in legal proposals | 4 % |
| 9 numeric extremes | 0, negatives, leading zeros, 40-digit, 4,000-, 4,300-, 4,301- and 5,000-digit numbers in every numeric field; and pairs written to share a page: `(0, 65536)` with `(1, 0)`, then deleted | 6 % |
| 10 hostile names | the relation name of an edge replaced by SQL, shell, path, format and log-lookup strings and by newlines | 4 % |
| 11 many items | a legal item repeated 2 to 20,000 times, or a legal batch of up to 3,000 distinct additions | 3 % |
| 12 one huge line | a single line of 1 KB to 2 MB of random letters, digits and brackets | 0.5 % |
| 13 shape abuse | empty and whitespace-only text, doubled separators, deep or unbalanced brackets, trailing-separator variants | 1.5 % |
| 14 replay of the old | an earlier committed proposal sent again | 10 % |

The **independent reference** is a second implementation of the grammar and of the gate, written by hand from the parser's docstring and the gate's docstring (a character scanner, no regular expression, numbers kept as digit strings so it has no integer limit), holding its own copy of the state. For every proposal both are asked. Checks:
* **A1 (decision):** the front door's accept or refuse equals the reference's.
* **A2 (state):** the front door's graph equals the reference's graph, compared in full every 64 proposals and at the end of each segment, and by sizes on every proposal. A refused proposal that changed anything is found at the next full comparison.
* **A3 (escape):** no exception leaves `Runtime.propose`; any that does is caught by the harness, counted by type and family, the first example kept, and the proposal is treated as refused.
* **A4 (pager audit):** `Pager.audit()` (free, mapped and held blocks add up, no block in two places) and "no transaction left open" every 10,000 proposals and after any escape.
* **A5 (pages and services):** the set of mapped pages equals the set of pages of the graph's services, every 1,000 proposals.
* **A6 (injection):** none of the injection strings, alone or around a legal proposal, ever commits.
* **A7 (time):** the time of every `propose` call (`perf_counter_ns`): the largest, and the 99.99th percentile, for each family; for families 11 and 12, time against size.

**Part B: replay.** In each segment, the committed texts in order are played into a fresh `Runtime`; the graph and the set of mapped pages must equal the live ones (**B1**). Then every proposal of the segment in order, except texts over 256 KB (all of which are refused at the parse, before any page is touched), is played into a second fresh `Runtime`; the graph, the page-to-block map and the number of free blocks must equal the live ones (**B2**). A third run takes a copy of the live `Runtime` at proposal 50,000, plays the second half onto it and compares the end states (**B3**).

**Part C: a crash inside a commit.** A "crash" here is an exception raised inside the code, not a killed process: there is no disk in this model. (C1) For each of 20,000 sampled legal commits to one `Pager` (1 to 6 pages written or unmapped), an exception is raised after the m-th change to the page table or to the free list, for every m from 1 up to the last change. After each, `audit()` must pass and the page table must equal exactly the table before the commit or exactly the table after it. (C2) In `DistributedPager.propose` over 5 ranks, the coordinator "dies" after committing j of the 5 ranks, for j from 1 to 4, over 2,000 proposals; `check()` must pass (no rank diverged, every audit clean). A killed process with no log would simply lose its memory; what Part B shows is that a log of committed texts is enough to rebuild the state, which is a statement about a log the host would keep, not about anything in this model.

**Part D: many writers.** (D1) 32 threads, 5,000 transactions each, on one `Pager` (64 pages, 512 blocks), each transaction writing 1 to 3 pages and unmapping 0 to 2, with a monitor thread calling `audit()` every 5 ms; at the end `audit()` must pass and attempts must equal commits plus conflicts plus out-of-blocks. (D2) 32 threads, 20,000 proposals each, on one `Runtime` with **no lock** (the class is documented as one proposal at a time; this part measures what happens outside that), on a 10 by 10 coordinate range to make collisions common, with the interpreter's thread switch interval set to 1 microsecond. (D3) The same, with every `propose` call under one mutex that also appends the committed text to a log; the end graph must equal the reference replay of the log, and the pager audit and the pages-and-services check must pass.

## Predictions (mine, written first)
Each line carries my probability that it reads "yes". A line that comes out "NO" is a finding, not an error.

1. [instrument] all 10,000,000 proposals were run, each family has at least 50,000 proposals, and the reference agreed with the front door on the 5,000 legal and illegal proposals written to test the reference itself before the run (95 %)
2. [guard] no exception escapes `Runtime.propose` in any family (10 %): the probe above shows one case
3. [guard] no exception escapes in any family other than family 9 (numeric extremes) (65 %)
4. [guard] A1: the front door's decision equals the reference's on every proposal that did not raise (90 %)
5. [guard] A2: the front door's graph equals the reference's at every comparison (92 %)
6. [guard] A4: the pager audit passes and no transaction is left open at every check (97 %)
7. [claim] A5: the mapped pages equal the pages of the services at every check (25 %): the page formula can give two services one page
8. [claim] A6: no injection string, alone or around a legal proposal, ever commits (97 %)
9. [claim] A7: no `propose` call in families 1 to 10, 13 and 14 takes more than half a second (90 %)
10. [claim] A7: for families 11 and 12 the time per byte at the largest sizes is at most 3 times that at the smallest (75 %)
11. [guard] B1: replaying the committed texts rebuilds the live graph and the set of mapped pages in every segment (93 %)
12. [guard] B2: replaying every proposal rebuilds the live graph, the page-to-block map and the free count in every segment (88 %)
13. [guard] B3: replaying the second half onto a copy taken in the middle equals the live end state in every segment (90 %)
14. [claim] C1: a crash after any change inside `Transaction.commit` leaves an audit-clean pager whose table is exactly the old one or exactly the new one (10 %): the commit changes the table and the free list in place, with no undo
15. [claim] C2: a coordinator crash between the commits of the 5 ranks never leaves the ranks diverged (5 %): there is no recovery log
16. [guard] D1: 32 threads on one `Pager` keep every audit clean, and attempts equal commits plus conflicts plus out-of-blocks (95 %)
17. [claim] D2: 32 unlocked threads on one `Runtime` raise no exception, keep the graph well formed, the pager audit clean and the pages-and-services check true (20 %): outside its documented use
18. [claim] D3: with the one mutex, no exception, and the end graph equals the reference replay of the log, with the audit and the pages-and-services check passing (90 %)

Of these, lines 2, 7, 14, 15 and 17 are the ones I expect to read "NO". That all 18 read "yes" I rate below 1 %.

What would count against AXI here: an exception that escapes the front door, a refused proposal that changed the state, a text that holds an injection and commits, a replay that does not rebuild the state, or a state left inconsistent by a crash. Each is reported as it is, with the first example kept, and read as a finding about the reference model, not as a result about the Rust crate (`crates/axi-cache`), which this test does not touch.

## Honest limits
The Python reference model, not the Rust crate; one interpreter, one version (the integer-string limit is a setting of CPython 3.11 and later, and a host that lifts it would see a different result on line 2); 14 families chosen by me, not the set of all hostile text; the independent reference is written by the same author and the same assistant as the harness, so a shared misreading of the docstrings would not show; a "crash" is an exception, not a killed process, and nothing is written to disk; 32 threads inside one CPython process share the global interpreter lock, so this is not 32 cores or 32 machines; the unlocked `Runtime` in D2 is used outside its documented contract; throughput figures belong to a two-core sandbox. Nothing here says a model's replies look like this text; Test 21 and the tests after it are where a model writes the replies. A fix to anything this test finds is made in a separate commit with a test and the run is repeated on a new seed; the framework is not edited to make a line pass.

**What happened that the plan did not foresee, and how it is read.**
* **This is the third full run, and the harness changed twice after the page was written.** A short smoke run before the first full run (4 segments of 4,000 proposals, which use the same seeds as the first four segments of the real run, plus parts C and D at full size) already showed the main findings below (the long-number exception, pages against services, C1, C2, the unlocked-thread errors); it also showed a harness bug (the pager audit was called with the wrong object), fixed before the first full run. The first full run finished parts A to D (A and B 7,431 s) and then crashed in the scoring code (a division by zero: the smallest size bucket of families 11 and 12 holds empty texts, so zero bytes); no result file was written, so its part A and B figures are lost; the scoring skips zero-byte buckets now and the raw merged results are saved before scoring. Its part C and D figures were printed before the crash and are the same as here for C1 (0 of 113,017 clean) and C2 (0 of 2,000 clean) and D1; D2 had 46 escapes in 92,183 commits there (37 in 92,137 here: thread timing is not repeatable) and D3 had 94,814 commits and no escape. The second full run was stopped at 25 of 100 segments when the sandbox restarted; per-segment checkpointing was added and this third run, with the same seeds, is the one reported. The harness changes were made before any full-size figure of lines 1 to 13 had been seen (the smoke run had shown small-size ones, as said above). The harness file named above is the one this run used.
* **Line 12 failed because of an assumption on this page that was wrong; it was found after the run.** The plan said texts over 256 KB are replayed in no replay because "all of them are refused at the parse, before any page is touched". In the two segments where the full replay did not match (segments 75 and 94) there were 164 and 177 such texts; 116 and 141 were refused at the parse, **48 and 36 at the gate, after the pager had written pages and given them back**. A refused proposal at the gate leaves the graph and the set of mapped pages as they were, but it can leave the pager's free list in another order (same set of blocks; in a re-run of the first 20,000 proposals of segment 75, 1,373 of 5,936 gate refusals did, and no parse refusal did). A replay that leaves such texts out therefore ends with the free list in another order and, in segment 75, with one page on a different block. Re-running the two segments with the oversized texts replayed too: B1, B2 and B3 all matched in both. The other 98 segments were not re-run (they matched under the skip rule). Also, the code compares the free list as an ordered list, while the plan page says "free count": in segment 94 only the order differed (17,547 free blocks in both); in segment 75 the graph and the free set also differ and one page sits on another block, so it fails under the plan's wording too. The checks and their outputs are in `docs/results/axi_gate_stress_after_run_checks.txt` (sha256 `8e4bc17b19aa3be16f091851c4c6937e2596a28b95a02046b97618b912eeb2bc`).
* **Line 1 reads NO by its letter for a reason that is my plan's, not the model's:** each proposal draws its family at random by its share, so a family with a 0.5 percent share (family 12) gets about 50,000 and, this time, 49,967 (all 10,000,000 ran; the reference agreed with the front door on 5,000 of 5,000 of its own test texts for parse and for decision).

Family 1 (legal) 2,000,575 proposals, all committed; family 9 (numeric extremes) 599,746, 279,577 committed, 230,337 refused, 89,832 raised; family 2 (mutated) 1,500,228, 67,436 committed, 1,431,681 refused, 1,111 raised; family 14 (replay of the old) 1,000,534, 362,442 committed. **Against AXI, as the page said it would be read.** *An exception escapes the front door:* yes, 90,943, one kind (the integer limit, a host-setting of CPython 3.11 and later, which a host program can switch off). *A refused proposal changed the state:* the graph and the set of mapped pages never changed on a refusal (0 state mismatches); the pager's free list changed order on some refusals at the gate. *An injection text committed:* no, 0 of 1,401,041. *A replay that does not rebuild the state:* 2 of 100 under the rule written here, 0 of 2 with the oversized texts replayed. *A state left inconsistent by a crash:* yes, in every one of the 113,017 crash runs of C1 and 2,000 of C2; these are the parts of the model with no undo and no recovery log, as the page said, and the Rust crate was not tested. Nothing was fixed here: the framework is as it was, and a fix would be its own commit with its own test and a new-seed re-run.

**In plain words.** Ten million hostile and random proposals went through the front door of the Python reference model. The things the host holds, the graph and the set of accepted changes, were exact against an independent reference at every comparison; no injection text ever got in; replaying the committed texts rebuilt the state every time; one lock around the door made 32 writers safe. Four things need work, and the run found them as they were: a number with 4,300 or more digits makes Python's own limit raise an error out of the door instead of a refusal; two services whose coordinates land on one page can unmap each other's page; a crash in the middle of a commit leaves the pager failing its audit, and a crash between ranks leaves the ranks apart; and without a lock, 32 threads raise errors (the class is documented as one proposal at a time).
