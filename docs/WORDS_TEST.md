# Ordinary-words test: can the scope filter read a request written in words? (written BEFORE any model run, 10 Oct 2026)

This page fixes the question, the predictions and the reading rules before any number exists. It follows `SCOPE_TEST.md` (named scope by coordinates), whose own limits section calls requests in ordinary words "the largest open question". Code: `python/axi/engine/grounding.py` (reading a request against a name table), its hook in `python/axi/engine/scope.py` (`names=`), `python/axi/experiments/cascade.py` (policy `scope_words`), `python/axi/experiments/word_tasks.py` (the tasks and the prompt), `python/axi/experiments/word_test.py` (runner, reading rules). Checks without a model: `python/tests/test_grounding.py`. Concept-map item 87 (rows 3, 9, 27).

## The question, in plain words
The scope filter keeps only the changes a request is about, and it finds out what the request is about by reading coordinates written in the text ("Delete the service at (2,1)"). A person writes "remove the billing service". With no coordinates the filter sees nothing named and falls back to plain ground-and-complete (M6): it is exactly M6 on a word request, so the protection that scope gave at 7B and 14B (16 more tasks right with the rule stated) is not there.

The idea tested here is the simplest one that can fail: the host keeps a **table of service names** (and a few aliases), and the request is read against it. A name or alias that appears as whole words is bound to its service (longest match first); a leftover word that is part of exactly one name is bound; a phrase that fits **two or more** services makes the request **ambiguous** and the filter applies **nothing** (it does not guess which was meant); a phrase that fits none, with nothing else named, applies nothing. The model never sees this code.

Two things are measured. (1) Does the filter keep its benefit when the request is in words? (2) Is it safe when a name is ambiguous, where today's policies (and the raw model) pick one and change the graph?

## Design
* **Tasks.** The same 140 graphs, kinds (20 of each of seven) and correct changes as `make_scope_tasks(140, 7)`, with the request written in words (`word_tasks.make_word_tasks(140, 7)`): "Remove the billing service.", "Decommission mailer.", "Remove the dep link from auth to cache with weight 3.", "Remove the cache service, and also the owns link from audit to ledger with weight 5.", "Add a dep link from inventory to audit with weight 3.". `delete_weight` is unchanged (it names nothing). `add_node` keeps its coordinates ("Add a new service called inventory at (4,2) with value 5.") because the new name is not in the table yet. About one in three mentions of a service that has an alias uses the alias. Every service has a different name; the name pool shares no word between entries, so a name written in a request fits exactly one service.
* **Ambiguity tasks.** 20 more requests (`make_ambiguity_tasks(20, 7)`): the graph has two services that share their first word ("billing api", "billing worker"; five such pairs), and the request names only that word ("Remove the billing service."). The correct reaction is **to change nothing**; the expected graph is the graph as it was. This is a design choice of ours (in a deployed system the right reaction might be to ask); here "apply nothing and say why" stands for it.
* **Prompt.** The system text of every earlier run, plus one line saying that services have names listed under Names and that replies always use coordinates, plus one worked example of a node delete (`remove the service called "demo", which sits at (2,1) -> DEL[2,1]`; the first hosted-model run showed `DEL[2,0:7]` written for `DEL[2,0]` in 12 % of replies, almost all of them in the rule-stated regime). The user text shows the graph, a legend ("Names: billing (also called ...) = (2,1); ...") and the request. **This is not the prompt of the earlier tests**, so numbers are compared with theirs only as numbers. Rule stated adds `RULES_HINT` as before.
* **Policies**, all evaluated offline on the same reply text: blind, gate, repair_m6 (never read the request); **scope_m7** (named scope by coordinates only; on a word request it is M6 by construction, the hole); **scope_words** (the new one). Success = the final graph equals the expected graph exactly; a graph with a dangling edge is corrupted.
* **Model and settings.** Gemini 3.5 Flash Lite through the free key, thinking and temperature at the model's defaults, at most 8,192 output tokens, one sample per distinct prompt, the same reply cleaning as `API_TEST_GEMINI.md` (one code fence and white space only). 160 requests in each of two regimes (no rule, rule stated) = 320 calls, inside one day's budget of 480. Every reply is saved the moment it arrives. A request in words is one more thing the model can get wrong (a wrong name-to-coordinates mapping); no policy can fix that, and it is reported as "both wrong".
* **Checked without a model** (`tests/test_grounding.py`, a design check, not a finding): the grounding finds exactly the services the request is about on all 140 requests for each of six seeds (840 requests), all 20 ambiguity requests of each of three seeds are read as ambiguous with exactly the two services, the correct change reaches the expected graph under scope_words on all 140 and leaves all 20 ambiguity graphs unchanged, and a model that guesses one of the two services changes the graph under blind apply, gate, repair_m6 and scope_m7 on all 20 and under scope_words on none.

## Predictions (mine, written first; the number is how sure I am)
1. [format] At most 5 percent of all the model's replies fail to parse (320 replies). (55 %) Reason for doubt: the slip of the first run (a number written after a node id) may survive the new example.
2. [guard] Gate, repair_m6, scope_m7 and scope_words corrupt **no** graph, in either regime, on the 140 or the 20. (99 %; by construction)
3. [guard] Ambiguous requests: scope_words changes the graph on **none** of the 20, in either regime. (99 %; by construction)
4. [need] Ambiguous requests: **blind apply changes the graph on at least 10 of the 20** in each regime (the model, which must answer with a delta, picks one or both). (80 %)
5. [need] Rule stated: **scope_words is ahead of repair_m6 by at least 5 of the 140.** (20 %) On this model the coordinate version gave no lead (0 helped, 0 harmed in both regimes of the first run), so I do not expect words to give one either; the finding I expect is "no harm, no help on the 140, and the whole gain is the refusal on ambiguity".
6. [guard] scope_words **harms at most 2 of the 140** in each regime (repair_m6 right, scope_words wrong). (88 %)
7. [guard] scope_m7 is **within 2 tasks of repair_m6** on the 140 in each regime. (92 %)
8. Not a verdict line. No rule: blind apply is right on **at least 110 of the 140** (the coordinate version: 120). (70 %) The best policy is wrong on at least 10 of the 140 because the model mapped a name to the wrong coordinates or made some other error nobody can repair ("both wrong"). (60 %)
9. Not a verdict line. The mean time of one reply is **between 0.3 and 3 seconds**. (80 %)

Overall: that every verdict line comes out "yes" I rate about **7 %** (line 5 alone is at 20 %); that every [guard] and [format] line does, about **45 %**. I expect line 5 to be "NO" and I expect that to be the main finding: the words filter is safe and gives a refusal that today's policies lack, and it adds nothing on the 140 on this model.

## Reading rules (fixed now; the notebook prints exactly these)
Seven lines, tagged **[guard]**, **[need]** or **[format]**: (1) [guard] gate, repair_m6, scope_m7 and scope_words corrupt no graph in any regime (the 140 and the 20); (2) [guard] ambiguous requests: scope_words changes the graph on none of the 20 in every regime; (3) [guard] scope_words harms at most 2 of the 140 per regime; (4) [guard] scope_m7 within 2 tasks of repair_m6 on the 140 in each regime; (5) [need] ambiguous requests: blind apply changes the graph on at least half of the 20 in each regime; (6) [need] rule stated: scope_words is ahead of repair_m6 by at least 5 of the 140; (7) [format] at most 5 percent of the replies do not parse (integer arithmetic, 20 times the unparsed count at most the number of replies). Code: `word_test.verdict_words`, `word_test.verdict_words_format`.

**How the result will be worded.** Format line "no": the other lines are read first as a statement about formatting, and the page says so before anything else. A [guard] line "no": a finding about the framework, looked into before anything is claimed. A [need] line "no": the raw model or the old filter does not fail there, reported with the numbers. A line that comes out "NO" is a finding, not an error. Nothing on this page is a statement about requests in general: the request styles are the ones generated here, and the table of names is supplied by us.

## What this cannot show
One model (Gemini 3.5 Flash Lite, not a Pro or frontier model); sampled replies, one per prompt, so a second run would not repeat the exact numbers. **Synthetic English requests built from three or four templates per kind**: a paraphrase outside the stop list of `grounding.py` ("kill the thing that charges cards") is unresolved, and a request in a style the stop list does not know is refused when it names nothing else, so the filter will over-refuse real requests until its vocabulary grows. **The name table is given, not learned**: a wrong table gives a wrong filter. **No language understanding is claimed**: grounding is exact and word-overlap matching against a table. The ambiguity result defines "correct" as "change nothing", which is ours. Single requests only: no long-horizon run here. No claim about latency (the grounding takes microseconds, not measured on this page) and none about savings.

## How it is run
A Colab notebook on a free CPU runtime (`python/colab/axi_words_test.ipynb`): upload the code zip, install the Gemini library, connect Drive, read the key from Colab Secrets, pick the model, then one cell per regime (no rule, rule stated), each printing the table and the reading-rule lines and downloading its result file; the reply file is saved to Drive. Each cell stops by itself at the day's budget and says when to run it again.
