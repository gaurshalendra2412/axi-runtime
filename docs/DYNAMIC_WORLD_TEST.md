# What does the host layer do when the proposer is not a language model and the world changes by itself? A stale-snapshot test (written BEFORE the run, 17 Oct 2026)

This page fixes the question, the design, the measures, the predictions and the reading rules before any arm rate from this test exists. Code: `python/axi/experiments/dynworld.py`; instrument checks `python/tests/test_dynworld.py`. Concept-map item 102. It needs no GPU, no language model and no internet: numpy on a CPU (Codespaces is enough), a few minutes. The small network it uses is a file of the repository, `docs/results/axi_dynworld_net.npz` (sha256 `3426ca055461781f394222c00f727b0d0b9bac269645fef1681c6762c6f4c744`), made by the recipe that is in the code.

## Where the idea comes from, and how it is treated
On 17 Oct 2026 the owner pasted an AI-written roadmap (no author, no sources given; I have not checked with Rajnish Choubey that anything in it is his, so I attribute none of it to him). Its first section asks for a test in which the language model is replaced by "a small, trained neural controller", the task is a grid whose zones are nodes and whose paths are edges, and at every step there is a chance `s` that the physical world changes an edge or a node "without the agent asking for it". It says the test would validate "Topos Theory and Heyting Logic under sensor noise", and would measure "whether the continuous energy landscape (Attractor Manifolds) can mathematically 'snap' the agent's noisy, out-of-sync proposal into the nearest safe physical action, keeping the robot alive even when its internal map diverges from reality by s%". Concept-map item 102 already had this idea as planned: a proposer that is not a language model, and a world that changes while the proposer works. This page is that test.

What I can and cannot say about the mathematics in the roadmap: I searched the Python package (`python/axi`) for "heyting", "topos", "attractor", "voronoi" and "spinor" and found no code. So **this test does not test that mathematics and can say nothing for or against it.** What the repository has, and what is tested, is the discrete host layer: the gate (accept a change only if it matches the held state and leaves it well formed) and the repair (`diagnostics.ground_and_complete`: keep what is true in the held state, cut what is false, close the boundary by deleting what depended on a deleted service). The nearest thing in the code to "snap the proposal to the nearest safe action" is that repair. Whether it is the same thing as the roadmap's snap is not a question a test like this can settle; the test measures what the repair does, and the page says so in the words of the code.

## What is tested, and what is not
**Tested (CPU, no language model):** (1) a proposer reads a **snapshot** of the held state; before its proposal is applied the world changes by itself (a service or an edge appears or disappears), so the proposal was made on a state that is one change old; four ways of handling the proposal are compared on the same requests and the same changes; (2) with a proposer that is exact about the snapshot it is shown (this isolates the age of the snapshot) and with a small trained network (this adds the proposer's own mistakes, which are not a language model's mistakes); (3) how far each way's held state ends from the real state, over long episodes of 1,000 requests; (4) a proxy for "the robot stays alive": routes planned on the held map and walked in the real world.

**Not tested here:** a robot, a vehicle, a camera or a sensor; real noise (the change of the world here is a clean event that the host is told about, see "What this cannot show"); continuous state, energy landscapes, topoi, Heyting algebras; a language model as proposer under a changing world (a later test); the roadmap's other three tests (a toy model trained with spinor embeddings, a hyperbolic snap, a topological history), none of which this page touches.

## The world
Services sit on the cells of a 5 x 6 grid (30 cells); an edge is a directed `dep` link between two services, with a weight from 1 to 9; a service has a value from 1 to 9. An episode starts from 8 services on a 3 x 4 patch with 7 to 10 edges (the shape of `cascade.random_graph`, one relation only) and runs 1,000 steps. The **oracle** is the real world: it holds the true state.

**Requests.** One per step, drawn by the picker of the hard test on the oracle's state (`million_hard.pick_hard_task`; same mix, same caps of 24 services and 48 edges, same "20 tries, then every kind once" rule as `endurance.Stream.next`). Per 34 draws: add a service 7, add an edge 20, delete a service that has 1 to 3 edges (together with them) 1, delete a service that has 4 to 8 edges (together with them) 3, delete a service that has no edge 1, delete an edge 1, delete a service and, besides, a named edge 1. The oracle grows to about 20 services and 18 to 38 edges, as in the hard test. The proposers receive the request as a structured record (the kind, the service, the edge, the weight or value), not as a sentence.

**What a request means on a state** (`intent_delta`): add a service: that, unless it is there; add an edge: that, unless it is there or one of its ends is not; delete an edge: that, if it is there; delete a service (all four kinds): the service **and every edge it has in that state**, nothing if it is not there; delete a service and an edge: both parts, each only if still there. The meaning is applied to the state the host holds NOW, not to the state the proposer saw. A request about something that is no longer there therefore means "do nothing". This definition is mine; it is the reading of the picker's own ideal replies (a delete of a service goes with all its edges) carried to a changed state. It matters, because the repair is configured with the same reading (see "What this cannot show").

**Changes of the world.** At each step, with chance `s`, one change is drawn on the oracle's state, kind by weight: an edge disappears 35, an edge appears 35 (between two services that exist, weight 1 to 9), a service collapses 15 (it takes its edges with it), a service appears 15 (on a free cell, value 1 to 9). Two regimes for the choice of the item: `uniform` (any item of that kind) and `near` (an item that touches a service the request names, and a new service on the request's own cell if the request adds a service and the cell is free): the world changing exactly where the agent is working. `near` is a stress regime, not a model of anything; `uniform` is the neutral one. If no item fits, nothing changes this step. Noise levels: s = 0, 0.05, 0.1, 0.2 and 0.4 (0.4 is not small: two steps in five).

**Order inside a step.** (1) The request is drawn on the oracle's state. (2) With chance `s` a change of the world is drawn. (3) Each arm's **snapshot** is a copy of its held state as it was before the change. (4) The change lands on the oracle and on every arm's held state (a change that does not fit a held state, for instance an edge to a service that state does not have, is ignored by that state; this is the trusted channel, see below). (5) The proposer reads the snapshot and the request and answers. (6) The arm handles the answer on its held state, which is now one change newer than what the proposer saw. (7) The oracle applies the meaning of the request.

## The proposers
* **`exact`** answers with the meaning of the request on the snapshot it is shown. It is never wrong about the snapshot, so every difference it makes comes from the age of the snapshot. It is the control for the instrument and the isolation of staleness; it is not a model of anything.
* **`net`** is a small neural network written in numpy and trained in the repository: input 1,027 numbers (which of the 30 cells hold a service, which of the 900 ordered pairs of cells hold an edge, the kind of request in five bins, the request's service and edge ends as one-hot, its weight and its value divided by 9; no edge weights and no service values are in the picture), one hidden layer of 128 ReLU units, output 930 positions (30 cells and 900 ordered pairs) times 3 classes (nothing, add, delete), read by arg-max per position. The value of an added service and the weight of an added edge are copied from the request; the weight of a deleted edge is read from the snapshot. It has no knowledge of the rules; it is shown states and ideal replies. Recipe (`dynworld.TRAIN`): 120 clean streams of 500 requests (60,000 examples; no change of the world), 16,000 mini-batches of 256, Adam, learning rate 0.002 falling along a half cosine to 0.0002, softmax cross-entropy per position, 612 seconds on two CPUs. The network is not a language model; it is also not good: see the next section.

## The four ways to handle a proposal (the arms)
| arm | what it does with the proposal, on the held state of that moment |
|---|---|
| `blind` | applies it as written (deletes what is named if it is there, adds what is named, overwrites what is there) |
| `gate` | applies it only if the gate accepts it on the held state, otherwise does nothing |
| `retry` | like `gate`; if the gate refuses, asks the proposer again on the CURRENT held state and passes that second answer through the gate once more (this is the optimistic retry of a transaction system: a baseline added so that the repair is not set against a strawman) |
| `repair` | `cascade.next_state("repair_m6", …)`: keep what is true in the held state, cut what is false, complete the boundary (`degree_threshold` = 48, so that every dependant of a deleted service is deleted: the reading of "delete a service" in the oracle) |

Each (proposer, arm) pair holds **its own** state through the whole episode and starts from the oracle's start state. So a mistake of an arm stays in its state and the next request is answered on top of it; that is what a long run does and what the distance measures.

## What is measured
* **slip**: the step did not do what the request means on the arm's own state at that moment; precisely, the arm's new state is not its own held state (after the change) with the meaning of the request applied. A slip is a mistake of this step, whatever the past.
* **exact** and **distance**: the arm's state against the oracle's, after the step (distance = number of services and edges that differ, absent or with another value or weight; `long_horizon.distance`). This is where one slip stays. The mean distance over all steps and the mean distance in each quarter of the episodes (250 steps) are reported.
* **corrupted**: the arm's state has an edge to a service it does not have.
* **calls**: how many times the proposer was asked (retry: 1 plus its refusals).
* **routes** (the proxy for "alive"): at each step two services of the oracle's new state are drawn, and a shortest route between them is planned on the arm's new held map, edges read as two-way paths, and followed even when it leads through a service the map does not have. The route is **unsafe** if the real world lacks one of its stops or one of its legs; **missed** if the real world has a route and the held map has none. These are shares of the routes planned and of the routes possible. A route on a map is not a robot, and a "leg" is not a motion; it is a way to put a number on "the held map said the way was open and it was not".

## The experiment
Two regimes times five noise levels: ten cells. In each cell, 20 episodes of 1,000 requests, so 20,000 steps; both proposers and all four arms live in the same world (same requests, same changes, same order), so every difference between arms in a cell is a difference of handling. Seed 20261101; each episode has its own seeds for the start, the requests, the changes and the routes. The printout shows a **digest** of the requests, the changes and the oracle's states (it does not include the network's answers, which can differ in the last digit of a matrix product between machines and so change a few decisions; the counts of the network cells may therefore differ a little from machine to machine, the lines should not).

## What I looked at before locking this page (and what I did not)
I looked at: (a) hand-made cases, six stale proposals on a five-service graph, one per kind of staleness (an edge appeared at the service to delete; an edge the reply deletes has gone; an edge added to a service that has collapsed; the service or edge to add has appeared with another value; the named edge of a pair has gone; the service itself has gone), and what each arm does with each; they are in `tests/test_dynworld.py` and read as the text above says: `blind` leaves an edge that has appeared at a service it deletes, adds an edge to a service that has collapsed, overwrites a value or weight that has appeared meanwhile, and survives when an edge it deletes has already gone; `gate` refuses and leaves the held state as it was; `retry` fixes the refusals at the cost of a second call; `repair` does what the request means with one call. (b) the control, s = 0 with the exact proposer, on short runs: all arms exact. (c) bookkeeping identities on short runs (every step counted once, per kind and per change), without reading rates. (d) the network: it did not learn at first (1,500 mini-batches gave 14 % exact replies on clean streams, 6,000 gave 77 %), I lengthened the recipe to 16,000 and it gave **1,388 exact replies in 1,800 requests (77.1 %)** on six clean streams of 300 requests that it was not trained on (seeds 900 to 905); of the 412 replies that were not exact, 385 left something out and 110 added something that was not asked (the two overlap). Its loss on the training batches is 0.0035 per example, so it has learned the training examples much better than it generalises. I stopped there; I did not tune it further, and I chose nothing about it by looking at an arm.

I did **not** print, save or look at the share of slips, the distance, the routes or the calls of any arm in any run, with either proposer, before locking this page: the tests check identities and the control's zeros and print no rates. (I did look at how many changes of the world a short run drew: in 200 steps of the near regime at s = 0.4, 80, that is two steps in five, as it should be.) My estimates below are by hand from the request mix, the change mix and the six cases.

## Predictions (mine, written first)
Each line carries my probability that it reads "yes". They are the reading rules below, in the same order. A line that comes out "NO" is a finding, not an error. The first four lines are about the instrument (a guard that the run is sound, a control, and a check that the change of the world has teeth); a "NO" there means the rest cannot be read.

1. [guard] every cell of the run finished: all episodes ran all their steps, no request stream ended early, and the oracle's state was well formed at every step (95 %)
2. [guard] gate, retry and repair were never corrupted (no edge pointing at a missing service) at any step of any cell, for either proposer (96 %)
3. [instrument] control: with s = 0, in both regimes, the four arms of the exact proposer slipped on no step and held exactly the oracle's state at every step (98 %)
4. [instrument] the change of the world has teeth: with the exact proposer in the near regime at s = 0.4, blind apply slipped on at least 3 % of its steps and so did the gate (96 %)
5. [claim] exact proposer, every cell: repair slipped on no step (88 %)
6. [claim] exact proposer, every cell: retry slipped on no step (91 %)
7. [claim] exact proposer, near regime, s = 0.4: the retry asked the proposer at least 1.03 times a step on average, the repair exactly once a step (95 %)
8. [claim] exact proposer, near regime, s = 0.4: the gate does not come back: its mean distance to the oracle in the last quarter of the episodes is at least twice that of the first quarter (70 %)
9. [claim] exact proposer, near regime, s = 0.4: of the routes blind apply planned at least 1 % were unsafe (they used an edge or a service the real world does not have), and repair planned no unsafe route (85 %)
10. [claim] exact proposer, s = 0.4: blind apply's slip share and the gate's slip share are each larger in the near regime than in the uniform regime (95 %)
11. [claim] net proposer, s = 0, both regimes together: blind apply slipped on at least 5 % of the steps (the network's own replies are not always right) (98 %)
12. [claim] net proposer, s = 0, both regimes together: repair slipped on fewer steps than blind apply, than the gate and than the retry (90 %)
13. [claim] net proposer, near regime, s = 0.2: repair slipped on fewer steps than blind apply, than the gate and than the retry (87 %)
14. [claim] net proposer, near regime, s = 0.2: repair's mean distance to the oracle over all steps is smaller than that of blind apply, of the gate and of the retry (85 %)
15. [claim] net proposer, near regime, s = 0.2: of the routes planned, the share that were unsafe is for repair at most half of blind apply's, and blind apply's is above 0 (82 %)

**Headline A** (lines 4, 5, 6 and 7), the exact reader: if all four read "yes", then when the proposer is exact about what it saw, and only the age of its snapshot is wrong, the repair is as right as asking again (zero slips), costs one call a step where the retry costs more, and the instrument was able to hurt the other ways. The product of my four probabilities is about 73 %; they are positively correlated, and my single number is about **75 %**.

**Headline B** (lines 12, 13, 14 and 15), the trained network, near regime, s = 0.2: if all four read "yes", then with a proposer that makes its own mistakes the repair slips less than each of the other three, ends nearer to the real state, and plans fewer routes the real world does not have. The product of my four probabilities is about 55 %; they are positively correlated, and my single number is about **65 %**.

Why I think so, line by line. *Lines 1 to 4:* the stream is the hard test's picker, which found a request at every step in the earlier long runs; the run asserts that the oracle's own step passes the gate; the gate applies nothing it refuses, and on the garbage replies of an untrained network the retry and the repair left no edge to a missing service in short runs (line 2 asks for it over the whole run); the control is the six cases with no change; the teeth are the hurt I can compute by hand (about a sixth of the requests delete a service, three in five add an edge, and in the near regime at s = 0.4 about two steps in five carry a change that touches what the request names). *Lines 5 and 6 (88 %, 91 %):* by induction. The retry and the repair start every step from the oracle's own state, because they never slipped before, and what an exact reader says about a state that is one change old is either still right (nothing changes), or refused by the gate (a match fails, or an edge would dangle) and then re-read on the current state, or, for the repair, kept where true and cut where false. The retry's argument I find complete. The repair's argument depends on the repair doing, on a stale answer, what `intent_delta` says, and I checked six cases, not all; the 88 % is the chance that no seventh case exists in 200,000 steps. *Line 7 (95 %):* the retry asks again each time the gate refuses, which I put at 8 to 15 % of the steps at s = 0.4 near; the repair always calls once. *Line 8 (70 %):* a refusal leaves a difference between the gate's state and the real one that nothing removes (the oracle never asks to delete a service it does not hold, so nothing asks the extra service of the gate's state to go), so I expect the distance to climb; the doubt is saturation: if the gate's state is far from the real one after a hundred steps, the first quarter is already high and the ratio of 2 is missed. *Line 9 (85 %):* the blind arm's state holds edges to services that do not exist (that is what corrupted means), and a route over such an edge is unsafe; one in a hundred is low, but the repair's zero depends on line 5. *Line 10 (95 %):* the near regime puts changes where the request is. *Line 11 (98 %):* the network gives a wrong reply 23 % of the time on clean streams, and blind apply carries out every wrong reply. *Line 12 (90 %):* at s = 0 the retry and the gate do exactly the same (the second read returns the same answer, because the state is the same), so the repair must beat their common figure; and 385 of the network's 412 wrong replies leave something out, which I expect to be the edges of a deleted service, which the repair completes. *Lines 13 to 15 (87, 85, 82 %):* the same mechanism with changes of the world on top; the doubts are the replies that add something not asked (110), which look true to the repair and are kept, and the retry, which may get a better reply when the state it reads has changed.

What each outcome would mean, written now so that I do not read it afterwards to suit the numbers. *Lines 5, 6 and 7 yes:* the repair gets the freshness of a retry at the price of one call, for the kinds of staleness this world has, when the reader is exact; since my argument for it is an induction, it would be a confirmation of the argument and of the code and not a surprise. *Line 5 NO:* there is a stale case where the repair does not do what the request means; the first case the run prints is the one to study, and the harness has found a hole in the repair. *Line 6 NO:* the gate accepts a stale answer that is wrong, which would be a hole in the gate for this edit language. *Line 7 NO:* the refusals are rarer than I think; the repair's advantage in calls is small. *Line 8 yes:* a gate without a repair does not come back, in agreement with the 4,000-step language-model run; *NO:* the drift saturates early or corrects itself in this world. *Line 9:* if yes, the held map of the blind arm tells the robot the way is open when it is not at a rate that matters for one in a hundred routes. *Line 10 NO:* the near regime does not hurt more than the uniform one; the regime is then not a stress. *Lines 11 to 15 yes:* the repair, designed for the mistakes of a language model's replies, also reduces the mistakes of a network that is not one, in this world; this is the part of the page that is nearest to what the roadmap asks. *Line 12 NO:* the network's mistakes are not of the kind the repair knows. *Lines 13 to 15 NO:* with a changing world on top the repair does not win over the retry or the gate; the most probable reason would be the replies that add what was not asked.

## Reading rules (fixed now; the printout prints exactly these)
The fifteen lines above are the reading rules; `dynworld.verdict_dynworld` computes them from the saved result. "Every cell" means every (regime, s) cell of the run. A step is counted for an arm once; "slipped on no step" means zero over all 20 episodes of the cell. "Slip share" is slips over steps. In lines 11 and 12 "both regimes together" pools the steps of the two cells with s = 0. "The routes planned" are those for which the held map had a route; the unsafe share is unsafe routes over routes planned. "Mean distance over all steps" is the sum of the per-step distances divided by the steps of the cell. The quarters of line 8 are the steps 0 to 249 and 750 to 999 of each episode, pooled over the episodes of the cell. Thresholds, as in the code: line 4: 3 % and 3 %; line 7: 1.03 calls a step and exactly 1.00 for the repair; line 8: ratio at least 2 and the last quarter above 0; line 9: 1 %; line 11: 5 %; line 15: half, and blind's share above 0. A rule about a cell that the run does not hold reads "not run"; the real run holds every cell.

## What this cannot show
The "world" is a graph, the "controller" reads a flattened picture of it, and the numbers are about this instrument. Nothing is measured on a robot, a vehicle or a model of one; a route is not a motion. **The changes of the world are applied to every arm's held state as they happen: the host is told, correctly and at once, what changed; only the proposer's snapshot is stale.** That is the opposite of a misreading sensor, which the roadmap speaks of. A test where the host's own map is wrong and no one tells it needs something that observes the world (a second reader, a check against a trusted source), which the repository does not have; this is the most important difference between this test and the situation the roadmap describes. **The repair is given the reading of "delete a service" that the oracle uses (delete every dependant)** and the ideal of a step is defined the same way; so "the repair slips on no step with the exact reader" is partly by construction and is a check of the code, not a discovery. The staleness is exactly one change old; a proposer that is several changes behind is not covered. The exact reader is not a model. The network is trained and tested on the same generator of states and requests; it reads cells and ordered pairs, not a sentence; its mistakes (omissions) are not a language model's (a language model also invents and misreads). The retry is charged only in calls; in a real system the second read costs time, during which the world may change again. The `near` regime and the mix of changes are mine; every rate depends on them. The numpy matrix products can differ between machines in the last digit, so a few decisions of the network can differ; the digest does not cover them. The episodes are 1,000 steps; the 4,000-step language-model run is a separate result. Nothing is said about a topos, a Heyting algebra, an energy landscape or an attractor.

## Related work (from memory, not searched; check before citing)
Optimistic concurrency control, where a transaction validates what it read and aborts and retries when something changed: Kung and Robinson (1981); snapshot isolation and its anomalies: Berenson et al. (1995). The gap between the time of a check and the time of a use (TOCTOU) is an old class of bug in operating systems. In safe reinforcement learning and in control, a "shield" or a runtime-assurance monitor that replaces an unsafe action of a learned controller by a safe one is well known (Alshiekh et al., 2018, "Safe reinforcement learning via shielding"; the Simplex architecture of Sha, 2001; control barrier functions, Ames et al., 2017). Constrained decoding that keeps a language model's output inside a grammar is a different mechanism for a different failure. If these hold as I remember them, a monitor that refuses an unsafe step, and a retry that asks again on fresh state, are not new; what the page measures is how a repair that completes the step instead of refusing it compares with both, in this world, and how much of the damage comes from the staleness and how much from the proposer.

## How it is run
In Codespaces, in `python/`: `python -m axi.experiments.dynworld --out axi_dynworld.json` (a few minutes, CPU; the network is read from `docs/results/axi_dynworld_net.npz`). `--quick` runs a few seconds of a small sample, to see that it works, not to read. `--retrain` trains the network again with the recipe (about ten minutes) and writes it to `--net`; the weights will differ in the last digits from the saved ones. The digest printed at the end should be the same on any machine with the same code. The result file is JSON; send it back and this page gets a "Result" section without changing anything above this line.

Line 8 is the one place where I was wrong in direction, and it is a small one: the gate's distance does climb and stays up, but it climbs so fast that the first quarter is already more than half the last.

## Where my hand numbers were off
* **The network's own mistakes (line 11).** I wrote that the network gives a wrong reply 23 % of the time on clean streams "and blind apply carries out every wrong reply", which suggests about 23 % of steps. Blind apply slipped on **49.6 %** of the steps at s = 0. The 23 % was measured with every request read on the oracle's own state; in the run each arm reads its OWN state, and after its first mistake that state is no longer one the network was trained on, nor the one the request was drawn from. Section "What I read from it", item 3, has the evidence.
* **Line 8 (the gate does not come back), 70 %.** The ratio of the last quarter to the first is **1.70** (the line asked for 2): the distance is 7.87 in the first quarter, 12.74 in the second and 13.41 in the last. The doubt I wrote down, that it would saturate early, was the right one. In the uniform regime at s = 0.4 the ratio is 1.32.
* **Line 9 (blind apply's unsafe routes at least 1 %).** I called one in a hundred "low"; it is **18.6 %** of the routes blind apply planned in the near regime at s = 0.4.
* **The cost of the retry.** I put the refusals, and so the extra calls, at 8 to 15 % of the steps at s = 0.4 near; they are **9.5 %**. Lower than the middle of my range, inside it.

## What I read from it (derived afterwards; none of this was pre-registered)
1. **With the exact reader the damage is persistent more than frequent.** In the near regime at s = 0.4 blind apply slips on 6.68 % of steps, but its state holds an edge to a service that does not exist after 82.1 % (16,429 of 20,000) of the steps, and equals the oracle after 3.5 %. The gate is never ill-formed, but it equals the oracle after 3.1 %, its mean distance is 12.02 against 3.98 for blind apply, and **38.9 % against 18.6 %** of the routes planned on its map are unsafe. A refusal leaves the held map behind the real world (the service the oracle deleted is still there), and by the route measure that is worse than applying the proposal as written. This depends on two choices of mine: the host is told every change at once (so for the gate a refused step is the only way for its map to differ), and a right step is defined as the meaning of the request on the current state.
2. **For the exact reader, the repair's gain over the retry is the second read.** Both are right on every step. The retry asked the proposer 9.5 % more often at the worst cell (near, s = 0.4); at s = 0.2, 0.1 and 0.05 the calls a step are 1.051, 1.021 and 1.013 (1.015 in the uniform regime at s = 0.4), the repair always 1.000. In a real system the second read costs time during which the world can change again; this test does not charge that.
3. **For the network, the changing world is almost invisible; its own mistakes are not.** Between s = 0 and s = 0.4 the repair's slip share goes from 9.86 % to 8.43 % in the near regime and from 10.84 % to 9.12 % in the uniform one, and blind apply's from 48.67 % to 45.75 %. Every arm except the repair is wrong on about half the steps at every s (44.1 % to 50.5 %). The mechanism is the closed loop: each arm's state equals the oracle's at the start of only 116 to 211 of the 20,000 steps of a cell (6 to 11 steps an episode, the steps before its first mistake; a mistake made from an exact state happened 20 to 21 times in 20 episodes); after that, in my reading, the network reads a state it was not trained on, for a request drawn from the oracle's state that its own state does not match. I did not test that explanation separately. The same network that was right on 77 % of clean replies is wrong on half of the steps of its own long episodes.
4. **The repair, with the network, keeps the held map near the real one but not on it.** Mean distance 3.47 to 6.96 items (the oracle holds about 40 items) against 48.67 to 108.34 for blind apply, the gate and the retry; slip share 8.4 % to 10.8 % against 44.1 % to 50.5 %; unsafe routes 9.5 % to 12.9 % against 75.7 % to 84.0 %. By kind of request (table above): deleting a service with its dependants, which is what the repair is built for, slips 9 of 2,647 steps; choosing an edge does not: adding an edge 8.9 %, deleting an edge 39.0 %, deleting a service and an edge 51.1 %. The repair completes a cascade; it cannot know which edge was meant.
5. **The retry buys nothing with the network.** At s = 0 the retry and the gate do the same thing step for step (the second read of an unchanged state returns the same answer): the gate slipped on 10,066 steps of the near cell and the retry on 10,066. In the near cell at s = 0.4 it costs 1.30 calls a step for nothing.
6. **The repair's slip share with the network goes down as s goes up** (item 3). I did not expect it and I have not tested why. One candidate: the oracle's graph gets smaller as the world churns (24.1 edges a step at s = 0 and 19.0 at s = 0.4, uniform), and the network may do better on smaller graphs. That is a guess, not a finding.

## What this does and does not show about the roadmap's first test
* **"Topos Theory and Heyting Logic under sensor noise", "truth gradient", "continuous energy landscape (Attractor Manifolds)".** Nothing in this test touches them (there is no code for them in the package). The page said so before the run, and the result does not change it.
* **"Snap the agent's noisy, out-of-sync proposal into the nearest safe physical action."** What was measured is a discrete procedure, the repair. With a reader that is exact about its snapshot it was right on every step (partly by construction, see above) and cost one call. With a trained network that makes its own mistakes it did not make the network right: it kept the held map within about 3.47 to 6.96 items of the real one instead of 48.67 to 108.34, and left 9.5 % to 12.9 % of the planned routes unsafe. If a robot followed a route planned on that map, roughly one plan in ten would use a leg the real world does not have. That is better than the others (75.7 % to 84.0 %), and it is not "alive".
* **"Even when its internal map diverges from reality by s %."** Here the host's map does not diverge by itself: it is told every change. What diverges is the proposer's snapshot, by one change. The situation of a map that is wrong and that nobody tells is not tested; for it the host would need something that observes the world.
* **"A rigid gate crashes and rejects everything."** The gate refused single steps, and left its map behind (item 1). It did not crash.

**Not done and worth doing:** the version in which the host is not told about the changes (a second reader or a check against a trusted source, and a number of its own); a network trained on its own closed-loop states, or on noise, to see how much of items 3 and 4 is the distribution shift of this one; a language model as the proposer under a changing world; snapshots that are more than one change old; a second, independently written oracle and route check (mine are written by the same hand); the other three tests of the roadmap.
