# Hard million-token test on a current hosted model: 4,000 steps of Gemini 3.8 Flash on a dense job with strict rules (written BEFORE the run, 13 Oct 2026)

The request that came after the two earlier pages (`docs/MILLION_TOKEN_TEST.md` on an open 7B model, `docs/MILLION_TOKEN_TEST_GEMINI.md` on Gemini 3.5 Flash Lite): "use 3.8 Flash and make the test as hard as you want; I am ready to pay; let's get something concrete out of it if it passes." This page is that test. A model is shown the exact state of a service graph at every step, is asked for one change, and the framework (scope_m7) decides what to keep; this is repeated for 4,000 requests in a row, about 2.9 million tokens, and the held state is compared with the right one at every step. Nothing is stored in a model's context from one step to the next, so what can go wrong is in the held state, in the replies the code cannot read, in the speed, or in the model's own slips; those are what is read.

**What this is and what it is not.** One model: Gemini 3.8 Flash (`gemini-3.8-flash`), a current hosted Flash model from Google. It is **not** a Pro model, and every sentence about it says "3.8 Flash". One job family (a service graph, requests that each name their targets by coordinate), run once on one stream seed with sampled replies, so one run is one sample and a repeat would write another history. The reading rules are **stricter than on both earlier pages** and are fixed below before any call. **A pass of this page is a pass of a much harder test; a NO is a number about this model on this job, not a verdict on the framework** (the section "How the result will be worded" says exactly what each outcome allows me to write).

## What is harder than on the earlier pages (all fixed here, before any call)
* **A dense graph.** Up to 24 services and 48 edges (the earlier pages: 14 and 26). On the oracle's stream the graph holds 17 to 22 services and 18 to 37 edges on average in each tenth of the two seeds. A prompt is on average 1,415 characters (the earlier page: 927), about 1.5 times as long, and most services have several dependants.
* **A new kind of request, `delete_hub`.** "Delete the service at (r,c)." where that service has 4 to 8 edges in or out. The right reply names the service and **every one** of its edges (on average 5.8 to 6.0 edges for a hub delete; the earlier pages stopped at 3), and, as on every page, **the rule that dependants must go too is not stated to the model**. Hub deletes are 8.1 to 8.7 percent of the steps; all deletes together about 21 percent; the share that has dependants (delete with dependants, hub, and service plus edge) about 15 percent.
* **A re-ask.** When the strict parser cannot read a reply, the model is asked again, up to twice (`million.reask_messages`: the same prompt with a short note after the request that says the reply could not be read; the second note differs from the first so that the saved reply is not returned). The saved Flash Lite runs showed unreadable replies on deletes (`DEL[r,c:v]`), and a reply that says nothing is the one slip the scope filter cannot see. Every attempt is stored and **billed**; the step is stored with the first reply, the other attempts and the one used, and the replay checks all of it.
* **The repair deletes up to 8 dependants (`degree_threshold=8`).** The framework's repair has a built-in rule: a deleted service with more than 4 dependants is **kept** rather than deleted together with them (a safe default). I found this in a stand-in program, not in a model: a program that deletes only the named service and forgets its dependants leaves the framework with a service the oracle has deleted, for every service with 5 to 8 dependants, and the distance then stays. The oracle of this test deletes the service and everything that depends on it, so for this test **I set the repair to delete up to 8 dependants before any call**; the value is written into the header of every file, the framework's default is unchanged, and this page does not claim that the safe default is wrong for other uses.
* **Strict reading rules.** Every tenth of the run at least 80 percent exact, at least 90 percent exact overall, a distance that never passes 4 items, at most one step in a hundred that does not do what was asked, at most 0.5 percent of steps ending with an unreadable reply (after the re-asks); the earlier pages allowed 10 items, 2 percent unreadable, 80 percent in the last tenth only. The **headline** ("PASSED") needs nine of the lines at once (listed below).
* **4,000 steps instead of 3,600, and a second seed.** A paid run (the owner turns billing on; the notebook never does), with a **dollar guard** typed in by the owner: the run stops by itself when the saved answers have cost that much at the prices the owner typed in.

## What is run
* **Run 1 (the test).** One episode, stream seed 20261031, 4,000 requests, policy scope_m7, the hard stream (`million_hard.HardStream`), up to 2 re-asks, repair deleting up to 8 dependants. Each step is one call (plus re-asks) unless the identical prompt was already asked and saved (then the saved reply is used and not counted as sent). The model is shown the policy's own held state; the request is made on the oracle's state. After every step the file on disk holds the step; if the session stops, running the same cell again replays the saved replies through the same stream and policy, checks every saved flag and every re-ask, and carries on (`million.replay`).
* **Contrast.** On the first 400 requests of the same stream, blind apply, the gate and repair_m6, each with its own held state and the same settings as run 1 (re-asks, repair). Where a policy's prompt equals one already asked, the saved reply is reused.
* **Control (reported, not a reading-rule line).** scope_m7 **without** the re-ask on the first 1,000 requests of the same stream, so that the value of the re-ask is a measured number. Where a prompt equals one already asked in run 1 the saved reply is reused.
* **Run 2 (optional, for line 14).** The same as run 1 with stream seed 20261032.
* **Requests.** Kinds and weights of `million_hard.KINDS_HARD`: add service x7, add edge x20, delete with dependants x1, delete hub x3, delete leaf x1, delete edge x1, delete service and edge x1 (34 slots). Measured on the oracle's stream (4,000 steps, the two seeds): add edge about 60 percent, add service 18.5, hub 8.1 to 8.7, delete with dependants 3.1 to 3.5, delete leaf 2.8 to 3.2, delete edge 3.0, delete service and edge 3.2 to 3.7.
* **Measured at every step.** Prompt tokens, visible reply tokens and **thinking tokens** (the service's own counts) of **every call of the step**, seconds of the successful calls, whether the strict parser accepted the reply, whether the held state is well formed, the distance to the oracle, whether the held state equals the oracle's, whether the step started from the oracle's state, whether the requested change could be applied as written to the held state, and if so whether the step did it; for a re-asked step the first reply and each attempt.
* **Model and settings.** `gemini-3.8-flash` (the notebook looks up the id the key can see and records it in the file), sampling at the model's default temperature, **thinking at the model's default unless the 20-step check says otherwise**, at most 8,192 output tokens including thinking, no grammar, the same system text and user text as every earlier run, the rule about deleting dependants NOT stated.
* **The 20-step check, and the one decision it can make.** Before run 1 the notebook runs a check on a different stream (seed 99, the hard stream). The first 200 requests of it are answered by the oracle itself (no call, nothing counted as sent) so that the graph has grown to the size of the real run, and the model is asked the next 20: on average 20 services, 25.9 edges and 1,406 characters a prompt (the run: 1,415 and 1,442), with 2 hub deletes and 2 deletes with dependants among them. It prints tokens a step, thinking tokens a step, seconds a call, the projected total, and the projected cost at the prices typed in. Twenty calls say how big the thinking and how long the calls are; they say nothing reliable about accuracy. **If it shows more than 150 thinking tokens a step, or a projected time of calls for run 1 of more than 4 hours, THINKING is set to "low" before run 1** (thinking tokens are billed as output and slow every call; "low" is the lowest level this model is said to accept: it is said to have no "minimal"). It is the only setting that may be changed; it is decided before run 1 is started and the Result says which was used. If the projected cost of run 1 is above the budget typed in, nothing is changed: the owner raises the budget or the run is not started. No other setting, threshold or line is changed after seeing any output.
* **Money.** The notebook never turns billing on (the owner does that in Google AI Studio), prints no dollar figure from a built-in price, and **refuses to start unless two prices and a budget are typed in**. Free tier: about 20 calls a day are said to be allowed for this model, which is enough for the 20-step check and nothing more. Two guards: the dollar budget (`api_llm.DiskCachedLLM`: before every real call, the saved answers are priced at the typed-in prices, thinking tokens as output; once they cost the budget the next call is refused and everything finished is kept) and a cap of 8,000,000 tokens on each run, whatever the price.

## What was seen before this page was written
* **No call was made to this model, on any stream.** I have never seen one of its replies. (Part B of the earlier API test, 20 calls to this model on the free quota, has not been made either.) Only the oracle was run: both seeds were generated for 4,000 steps to check that the stream does not end early (it does not), that it stays inside 24 services and 48 edges, and how big the graph is (17.1 to 22.2 services and 18.4 to 37.0 edges on average in the ten tenths of the two seeds; the largest graph held 24 services and 48 edges).
* **How the request weights were chosen.** By searches on the oracle's graph only: 192 weightings tried on seed 20261015 (1,500 steps), 8 more by hand, and three finalists on four seeds, **among them the two seeds of this page** (sizes only, no model). The target was a graph that stays large (about 20 services, 18 to 37 edges) and about 15 percent of the steps with dependants. The weights above met it.
* **Token estimate.** The prompts of this stream, built on the oracle's states, are on average 1,415 characters (seed 20261031) and 1,442 characters (seed 20261032). The Qwen line (tokens = -256.8 + 0.6709 x characters, fitted on the shorter prompts of the earlier streams, so used here a little beyond the range it was fitted on) gives about 693 and 711 prompt tokens; the Flash Lite service counted 308.6 prompt tokens a step against 307.3 for Qwen on the same step mix, so about the same. A reply is about 31 characters, I guess about 20 tokens. My estimate is **about 720 visible tokens a step, about 2.9 million for 4,000 steps**, plus thinking tokens, which are unknown for this model.
* **Cost estimate (arithmetic on UNVERIFIED prices).** The prices I use, **$0.75 per million input tokens and $3.75 per million output tokens (thinking tokens count as output) for 3.8 Flash, said to double on 1 January 2027**, come from a pasted answer of another assistant; I could not check them and the owner must read the AI Studio price page before typing the prices in. Per run, with 702 prompt tokens and 20 reply tokens a step (re-asks add a few percent):

| thinking tokens a step | run 1 (4,000 steps) | contrast (1,200 steps) | control (1,000 steps) | run 1 + contrast + control | with run 2 as well |
|---|---|---|---|---|---|
| 0 | $2.41 | $0.72 | $0.60 | $3.73 | $6.14 |
| 100 | $3.91 | $1.17 | $0.98 | $6.05 | $9.96 |
| 300 | $6.91 | $2.07 | $1.73 | $10.70 | $17.61 |
| 1000 | $17.41 | $5.22 | $4.35 | $26.98 | $44.39 |

  So I expect **about $4 for run 1, about $6 with the contrast and the control, and about $10 with run 2 as well** if the model thinks about 100 tokens a step ("low"); $7, $11 and $18 at 300; the default of the model could be worse, which is what the 20-step check and the dollar guard are for. I suggest typing a budget of 15 dollars first. The cost is not a result of this page.
* **What shaped the probabilities.** The saved Flash Lite tests on the earlier, easier mix (`docs/API_TEST_GEMINI.md`, Part A, seed 7, thinking and temperature at the default, no rule stated): 4 episodes of 30 steps, **scope_m7 and repair_m6 held the oracle's state on 120 of 120 steps**, 0 corrupted, 0 unparsed; blind apply held it on 61 of 120 and a corrupted graph on 59, 3 of 4 episodes were corrupted at some step (first at step 3, 13 and 14), all from a delete of a service together with an edge, where the raw model left a dangling edge on 15 of 20 requests; on a delete with dependants it was right 20 of 20 without help (the 7B was right on none), and those had at most 3 dependants. 3 of 140 single replies were unparsed with no rule stated (all on deletes), 0 of 177 in the long runs; with the rule stated, 75 of 334 replies were unreadable, all the same slip. **Nothing is known about legal-but-wrong replies on a dense graph, and nothing about hubs of 4 to 8 dependants.** The persistence of an offset is what makes the exactness lines hard: a wrong edge or a lost delete stays until the cell is added again or the item is deleted in the oracle, which on this stream takes on the order of fifty to a hundred steps (my estimate from the churn: a given service lives about 110 steps on average, a given edge less). So 90 percent exact overall means **four to eight slips in 4,000 steps at most**, one slip in 500 to 1,000 steps; that is the bar, and it is high on purpose.

## Predictions (mine, written first; the number is how sure I am)
1. [guard] Run 1 reaches step 4,000 with every registered setting, and its replay reproduces every saved flag and checks every re-ask. (85 %) The doubts are the service (a run of one to three hours, a busy server, a silent change of the model), the budget (a typed-in limit that is too small stops the run, and that is reported as a stop), and a problem in the code I have not met. A run that stops before step 4,000 is reported as stopped at step N, line 1 reads NO, and the other lines printed for it describe the first N steps only.
2. [guard] scope_m7 is never corrupted. (99 %) The gate checks well-formedness on every step.
3. [instrument] At most 0.5 percent of the steps (20 of 4,000) end with a reply the parser refused, after the re-asks. (93 %) The slip was 3 of 140 single replies on the older model, all on deletes; the re-ask tells the model its reply could not be read, and I expect most of them to be rescued.
4. [instrument] Blind apply is corrupted on at least 80 percent of its first 400 steps. (55 %) This depends on the model leaving a dependant out of a delete reply early and often; the older model did it on 15 of 20 service-and-edge deletes and never on a delete with up to 3 dependants, and a hub has 4 to 8. If the model names every dependant every time, the raw state stays well formed, this line reads NO, line 13 reads NO with it, and that is a result about the model, not a failure of anything.
5. [claim] Run 1 sends at least 2,500,000 tokens. (90 %) My estimate is 2.9 million visible tokens before thinking; this fails only if a step costs less than 625 tokens, or the run stops early.
6. [claim] In every one of the ten tenths, at least 80 percent of the steps hold exactly the oracle's state. (30 %) **This is the line I expect to fail first.** One slip keeps the state off for fifty to a hundred steps, so a tenth of 400 steps can hold at most one or two slips.
7. [claim] At least 90 percent of all steps hold exactly the oracle's state. (40 %) Four to eight slips in 4,000 steps at most.
8. [claim] The distance to the oracle never exceeds 4 items. (45 %) A lost hub delete (a refused reply after the re-asks, or a reply naming another service) leaves the service and its 4 to 8 edges: a distance of 5 to 9 at once. With about 330 hub deletes in the run, one such step is the doubt.
9. [claim] The mean distance in the last tenth is at most 0.5 above that of the first tenth. (65 %) Both tenths are small numbers, and a single long-lived offset in either decides it.
10. [claim] Among steps that start from the oracle's state and ask for a change that can be applied, at most 1.0 percent did not do what was asked. (80 %) That is 40 of 4,000; a model with 99.5 percent per-step accuracy passes this line and fails lines 6 and 7.
11. [claim] The mean prompt tokens in the last tenth are at most 1.5 times the first tenth's. (97 %) The stream moves the prompt by 10 to 17 percent between those tenths (1,302 against 1,451 characters on seed 20261031, 1,309 against 1,525 on seed 20261032).
12. [claim] The mean seconds a step takes in the last tenth are at most 1.5 times the first tenth's. (60 %) A hosted service's speed moves with its load, and the seconds of a re-asked step are the sum of its attempts.
13. [claim] In steps 201 to 400, scope_m7's mean distance is at most 0.5 and smaller than blind apply's and than the gate's. (45 %) It needs the raw model to break the state (line 4) and scope_m7 to stay within two slips. If the model is perfect on those 400 steps, all three policies read 0 and this line reads NO because "smaller" fails.
14. [claim] Only if run 2 is made: it also reaches step 4,000 with the registered settings, lines 2, 3 and 6 to 12 also hold for it, and the two runs together sent at least 5,000,000 tokens. (8 %) Nine conditions at once, among them the two I expect to fail first, on a second sample.
15. Not reading-rule lines. The 20-step check shows more than 150 thinking tokens a step at the default, so that "low" is used (65 %). Tokens sent in run 1 are between 2.8 and 4.0 million (60 %). The projected cost of run 1 at the typed-in prices is between $2 and $8 (65 %). The mean seconds of a call are between 1.0 and 5.0 (65 %). The share of first replies the parser refused is between 0.1 and 2.0 percent of the steps (60 %), and of the steps that needed a re-ask at least 80 percent ended readable (75 %). In the control, the steps that ended refused are more than in the main run's first 1,000 steps (65 %). The share of steps equal to the oracle over the whole run is between 60 and 99 percent (65 %). Of the steps where the held state first leaves the oracle's (start equal, end not), more than half follow a readable reply that did the wrong thing and not a refused one (65 %), and the largest count of such slips is among the add-edge requests, which are 60 percent of the steps (60 %).

Overall: that all nine headline lines of run 1 (lines 1, 2, 3, 5, 6, 7, 8, 9, 10) come out "yes", which is what "PASSED" means, I rate about **20 %** (lines 6 to 10 are one question asked five ways: how often the model slips); that lines 1 to 4, the guard and instrument lines, all do, about **43 %**; that all fourteen lines are "yes", **under 3 %**. **I expect a NOT PASSED, and the interesting numbers then are the count of slips per thousand steps, their kinds, and what the re-ask bought.**

## Reading rules (fixed now; the program prints exactly these)
Fourteen lines, tagged **[guard]**, **[instrument]** or **[claim]**, answered "yes", "NO" or "not run" (lines 4 and 13 need the contrast, line 14 needs run 2). Code: `million_hard.verdict_hard`; the settings a run must have to be read as the registered one are checked by `million_hard.registered` and are part of line 1.
1. [guard] the main run (scope_m7, the hard stream, up to two re-asks, the repair deleting up to 8 dependants, one of the two registered seeds) reached step 4,000 with every step on file, and the replay of its saved replies reproduces every saved flag of every step and checks every re-ask
2. [guard] scope_m7 was never corrupted (no edge pointing at a missing service) at any step of the main run
3. [instrument] at most 0.5 percent of the steps of the main run ended with a reply the strict parser refused (after the re-asks)
4. [instrument] blind apply, on the same requests, was corrupted on at least 80 percent of its first 400 steps
5. [claim] tokens sent in the main run (prompt, visible reply and thinking tokens of every call, as the service counted them) are at least 2,500,000
6. [claim] in every one of the ten tenths of the main run, at least 80 percent of the steps hold exactly the oracle's state
7. [claim] at least 90 percent of all steps of the main run hold exactly the oracle's state
8. [claim] the distance to the oracle never exceeded 4 items at any step of the main run
9. [claim] the mean distance to the oracle in the last tenth of the main run is at most 0.5 above that of the first tenth
10. [claim] among the steps of the main run that start from the oracle's state and ask for a change that can be applied, at most 1.0 percent did not do what was asked
11. [claim] the mean prompt tokens of the last tenth of the main run are at most 1.5 times those of the first tenth
12. [claim] the mean seconds a step takes in the last tenth of the main run are at most 1.5 times those of the first tenth
13. [claim] in steps 201 to 400, scope_m7's mean distance to the oracle is at most 0.5, and smaller than blind apply's and smaller than the gate's, on the same requests
14. [claim] the main run on the second seed also reached step 4,000, and lines 2, 3 and 6 to 12 also hold for it, so that the two runs together sent at least 5,000,000 tokens (only if run 2 was made)

**The headline.** `million_hard.headline` calls the test **PASSED** if lines 1, 2, 3, 5, 6, 7, 8, 9 and 10 all read "yes", **NOT PASSED** if one of them reads "NO", and NOT DECIDED otherwise. Lines 4, 11, 12, 13 and 14 are printed and reported with the headline and are not part of it: line 4 and line 13 describe the raw model; line 14 is the replication; lines 11 and 12 are about cost and speed.

**How the result will be worded.**
* **PASSED.** The one sentence I allow myself, with the figures filled in from the file and nothing added: "On Gemini 3.8 Flash, in one sampled run of 4,000 requests (N million tokens sent) on a dense service graph (17 to 22 services on average), the held state kept by the framework (scope filter, deterministic repair deleting up to 8 dependants, up to two re-asks) was exactly the right state on X percent of the steps and at least 80 percent in every tenth, was never more than D items from it, and was never corrupted; blind application of the same model's replies was corrupted on Y percent of its first 400 steps (or: was not)." It does **not** allow "the model is accurate at a million tokens" (it never sees more than one state and one request), "this holds for any task or any model", "this beats a chat that keeps its history" (not measured), or a statement about price. Line 14 "yes" would add "and on a second seed".
* **NOT PASSED.** Reported as a limit, with the numbers: which of the nine lines failed, the count of new offsets (steps that start on the oracle's state and end off it) by cause, from the saved rows: an unreadable reply after the re-asks, or a readable reply that did the wrong thing, and by request kind; how long each offset lasted; the slips per thousand steps with the steps where the state was exact; and the control arm's number for what the re-ask bought. The lines and thresholds are **not** changed after the run; a harder or easier test is a new page. A NO on lines 6 to 10 is a statement about the model's own slip rate on this job at least as much as about the framework, and it will be worded that way: the scope filter and the repair keep what is true and cut what is false, but a reply that is readable, inside the request's scope and wrong (a wrong weight, a wrong endpoint) is applied.
* **Line 1 NO** is looked into before anything else is read: a crash or a replay mismatch is a bug to be fixed in a separate commit, with a test, and the run repeated on a new seed rather than edited; a stop by the service, the budget or the cap is reported as a stop. **Line 2 NO** is a finding about the framework. **Line 3 NO** means the re-ask did not rescue enough replies; the distance is then read together with the count of unreadable replies. **Line 4 NO** means the model did not break the raw state on this stream; it is reported as exactly that. **A NO on line 11** means cost per step grows with the length of the job; **on line 12**, first compared with the means per day and per tenth, because a hosted service's speed changes for reasons that are not the job's length.

## What this does not show
That a model is accurate "at a million tokens" in the sense of one conversation of a million tokens (the model never sees more than one state and one request); that any other model behaves like this one (a Pro model, another provider's model, a different release of this model); that another task, with state that must grow without a cap, would stay flat (this graph is capped at 24 services and 48 edges); that real users' requests look like these (each request names its targets by coordinate and is phrased in the same few ways); that the savings against a chat that keeps its history, or that caches its prefix, are real (that comparison is a separate test, not built; the history side is not run here); that a repeat would give the same numbers (replies are sampled; one run is one sample); that the safe default of the repair (keep a service with more than 4 dependants) is wrong. The comparison of the first and the last tenth compares two stretches of ONE stream, whose graph size moves by itself from tenth to tenth, so a small difference in either direction is not read as a trend. Cost in money is not a result of this page.

## How it is run
`python/colab/axi_million_hard.ipynb` with `axi-colab-million.zip` on Colab's free CPU runtime (no GPU is needed). The key lives in Colab Secrets and is never printed or saved. Billing is turned on by the owner in Google AI Studio for the key's project, and the owner types in the two prices and the budget from the AI Studio price page (the cell stops with a message if any of the three is missing). Cells 1 to 5 prepare, the 20-step check follows, then run 1 (about 4,000 steps; one to three hours of calls; progress shown every 100 steps and saved to Google Drive every 25), then the contrast, the control and, if wanted, run 2. If the session stops, or the budget is used, run Cells 2 to 5 again (raise the budget in Cell 5 if that was the reason) and then the same cell: it continues from the last saved step. The files that come back are read here by `python/tests/test_million_hard_result.py`, which recomputes every number of the Result below from them.
