# Does the way a dense graph is written change what a stock model can read from it? A representation test (written BEFORE the run, 15 Oct 2026)

This page fixes the question, the measures, the predictions and the reading rules before any answer of any model exists. Code: `python/axi/experiments/kv_dense.py`; instrument checks `python/tests/test_kv_dense.py`. Concept-map item 101. It needs a GPU model (the Qwen2.5-7B-Instruct 4-bit of the Colab notebook, a new cell at the end); the token counts (lines 4 and 5) need no model.

## Where the idea comes from, and how it is treated
On 15 Oct 2026 the owner pasted a text (author not stated to me; it speaks of "Choubey's Mapping (axi-ir)" and I have not checked with Rajnish Choubey that the formulations are his, so I do not attribute them to him). One part says that the framework "explicitly defines a relational density threshold", rho = |E| / (|V| (|V| - 1)); that when rho is at most 0.65 it "streams coordinate tuples to the model"; and that above it "text serialization causes catastrophic token bloat and attention confusion", so the framework "dynamically cuts over to Packed Bit-Matrix Representations (64-bit integer bitsets)", which the text calls "a massive, unmeasured efficiency lever". It gives no measurement.

I first answered by asking whether the repository already had it. The owner objected: a thing that is missing from the repository is a **new** thing, and not being there is no reason to set it aside. What I find in the repository, stated so that nobody has to trust the word "missing": `crates/axi-ir/src/router.rs` has a `DensityRouter` with the default threshold 0.65 that returns one of two labels, `SparseTuples` or `PackedBitMatrix` (two unit tests, no caller); it computes the density as (services + edges) divided by the cells of the grid, which is **not** the formula of the pasted text (by it, the sparse graphs of this test, 24 services and 138 edges on 25 cells, would be routed to the packed form too); and nothing in the repository turns the label into text for a model. `python/axi/wire.py` is a binary frame with a coordinate form and a bit-matrix form, and `python/tests/test_wire.py` shows that the size crossover of that frame is at about 1/128 of the cells, not 0.65: that is a measured question about bytes on a wire. **What a model can read of either form has not been measured anywhere in the repository.** That is the question below, and it is a different question from the two above.

## What is tested, and what is not
**Tested (a stock model, reading only):** the SAME dense graph is written in five ways and the SAME questions are asked; I count the tokens of each way and score the model's answers. The same is done for a sparse graph, as the contrast the text itself draws.

**Not tested:** (1) the host side. A bitset is a textbook structure for a dense graph in Python or Rust; that it is small and fast there is not in question and nothing here bears on it. (2) A model that has been trained, or whose backbone has been changed, to read bitsets: the text's roadmap speaks of such a model; a stock model failing at the format says nothing about it. (3) The cut-over at rho = 0.65: the dense graphs here have rho = 0.725 and the sparse ones 0.25, so this test compares two regimes and cannot place a threshold. (4) The writing of edits (a model answering with a delta against a bitset); only reading. (5) Any model but one, any graph size but 24 services, any seed but one.

## The graphs and the five formats
24 services on a 5 x 5 grid (one cell empty; values 1 to 9), edges of the relation `dep` with a weight 1 to 9. **Dense:** 400 edges, rho = 400 / (24 x 23) = 0.725 (5 graphs). **Sparse:** 138 edges, rho = 0.25 (3 graphs). Seed 51.

| format | what the model is given |
|---|---|
| `tuples` | the repository's own text: `NODES [r,c:v] ...` and `EDGES (r,c)->(r,c):dep#w ...` (`CICOParser.serialize_state`); it carries the relation and the weight, the other four carry presence only |
| `adjacency` | one line per service: `(r,c) out: ...services it has an edge to... in: ...services that have an edge to it...`; every edge appears twice |
| `matrix` | the adjacency matrix: one row per service, 24 numbers 0 or 1 separated by spaces; the order of the columns is stated and the meaning of a 1 is stated |
| `binary` | the same rows as unbroken strings of 0 and 1 (character j counted from the left from 0) |
| `bitset` | each row packed as one 64-bit integer in hexadecimal, `0x` and 16 digits (bit j counted from the right from 0 is 1 if the service has an edge to column j); the order of the columns and of the bits is stated: this is the text's format |

Each of the 40 (graph, format) pairs is checked by a decoder that reads the prompt's state back the way the format says it is written; the edges it finds must be exactly the graph's.

## The questions and the scoring
Eight per graph, the same in every format: the services a given service has an edge to (2), the services that have an edge to a given service (2), and "is there an edge from A to B?" (4: two that exist, two that do not, in random order). The lists have at least one member and leave at least one other service out. The model is asked for the answer only, with greedy decoding, no grammar, 160 new tokens at most; every question is a fresh prompt (no cache is kept between questions). 64 questions per format: 40 on the dense graphs (5 x 8), 24 on the sparse ones (3 x 8); 20 and 12 of them are existence questions.

For a list: precision, recall, F1 and exact match against the truth (the asked service itself, if the model repeats it, does not count). For a yes/no: the share right (chance is 0.50, because the questions are balanced). Because a dense graph makes a lazy strategy strong, every list question also has a **baseline**: the F1 of answering with all the other 23 services (precision k/23, recall 1). On these dense graphs this is 0.83 (mean list of 16.5 services), on these sparse ones 0.36 (mean list of 5.2); a reading of the graph is worth something only above it.

## What the design alone fixes (computed before the run)
The count below is a LOWER BOUND of Qwen's token count (the number of pre-tokens of Qwen2's pre-tokenizer; the byte-pair merges can only split a pre-token further, never merge two). Digits are single tokens in Qwen and a space before a digit is a token of its own, which is why spaced matrix digits cost two tokens each. The run counts the real tokens of the model's tokenizer; this table is not a result.

| state, tokens (lower bound) | tuples | adjacency | matrix | binary | bitset |
|---|---|---|---|---|---|
| dense (rho 0.725) | 4,982 | 4,248 | 1,459 | 918 | 743 |
| sparse (rho 0.25) | 1,838 | 1,628 | 1,459 | 918 | 789 |
| dense, over tuples | 1 | 0.85 | 0.29 | 0.18 | 0.15 |
| sparse, over tuples | 1 | 0.89 | 0.79 | 0.50 | 0.43 |

Where the token counts cross, on the same count with 24 services and 3 graphs per size (edges: tuples / adjacency / bitset): 20: 422 / 469 / 791; 60: 902 / 851 / 790; 138: 1,838 / 1,628 / 789; 300: 3,782 / 3,248 / 767; 400: 4,982 / 4,248 / 742. By tokens the packed form is shorter than the tuples from about 60 to 70 edges, that is a density of about 0.11, not 0.65 (and the matrix forms from about 110 edges, about 0.2).

So the text is right that serializing a dense graph as tuples is big (about 5,000 tokens for 24 services) and that the matrix forms are 3 to 7 times smaller; the matrix forms have a fixed size whatever the density, which is why they do not pay on a sparse graph. Where a cut-over would pay in tokens is far below 0.65, as it is in bytes on the wire. Whether a model can USE the packed forms is what the run asks.

**Debugging before the page was locked:** the five renderers and decoders were run on the eight graphs (the round trip held); the token counts above were computed; no model was run on any question, and no accuracy or F1 was computed from anything.

## Predictions (mine, written first)
Each line carries my probability that it reads "yes". They are the reading rules below, in the same order. A line that comes out "NO" is a finding, not an error.

1. [instrument] Every format answered the same 64 questions (40 on the dense graphs, 24 on the sparse ones), and the questions of one graph are the same in every format. (99 %)
2. [instrument] In every prompt the state, read back by the decoder of the format, holds exactly the graph's edges (all 40 graph-and-format pairs). (99 %)
3. [guard] dense, tuples: the share of the 20 existence questions answered right is at least 0.60 (the model can read this text at all). (80 %)
4. [claim] dense: the `matrix` prompt holds at most 0.35 times the tokens of the `tuples` prompt (mean over the 5 graphs, by the pre-tokenizer count of the dry run, then by the tokenizer's own count in the run). (90 %)
5. [claim] dense: the `bitset` prompt holds at most 0.20 times the tokens of the `tuples` prompt (same count). (90 %)
6. [claim] dense: adjacency's recall on the 'who has an edge to X' questions is at least 0.15 above tuples'. (85 %)
7. [claim] dense: tuples' recall on the 'who does X have an edge to' questions is at least 0.10 above its recall on the 'who has an edge to X' questions. (75 %)
8. [claim] dense: matrix answers the existence questions at least 0.05 worse than tuples. (72 %)
9. [claim] dense: bitset answers the existence questions right at most 0.60 of the time (close to chance, which is 0.50). (80 %)
10. [claim] dense: bitset's mean F1 on the list questions is below the F1 of answering every list question with all the other services. (80 %)
11. [claim] dense: bitset is at least 0.10 worse than tuples on the existence questions AND at least 0.10 worse on the F1 of the list questions. (60 %)
12. [claim] dense: of the five formats adjacency has the highest mean F1 on the list questions. (65 %)
13. [claim] sparse: tuples answers the existence questions at least as well as matrix. (75 %)
14. [claim] sparse: adjacency's mean F1 on the list questions is at least tuples'. (80 %)

**Headline** (lines 4, 5, 9 and 11): if all four read "yes", then the text is right that the packed forms save most of the tokens on a dense graph and wrong, for a stock model, that this is a lever it can use: the model reads them at about chance and worse than the plain text. The product of my four probabilities is about 39 %; they are positively correlated for the last two, and my single number is about **45 %**.

Why I think so, line by line. *Lines 4 and 5 (90 %, 90 %):* arithmetic, from the table above; the real tokenizer can only raise the tuple count (the `)->(` run is split) and it leaves the one-digit matrix tokens as they are, so the real ratios should be at or below the lower-bound ones (0.29 and 0.15); the 10 % is for something about Qwen's tokenizer I have wrong. *Line 3 (80 %):* a 7B model at 4 bits, 5,000 tokens, an exact string to find or to find absent: I expect 70 to 80 % right, and 60 % is the floor under that, with 20 questions (a standard error of 0.1). *Line 6 (85 %):* in the tuple text the edges are sorted by source, so the edges INTO a service are scattered over 5,000 tokens and the model must scan for them (I expect recall 0.3 to 0.6); in the adjacency text they are one list on the service's line (I expect above 0.85). *Line 7 (75 %):* the same sorting makes the edges OUT of a service one contiguous block; I expect recall 0.7 to 0.9 for out and 0.3 to 0.6 for in. *Line 8 (72 %):* to answer from a matrix the model must find the row, then count to column j in 24 numbers; counting in a row of digits is a known weak point of such models; I expect 55 to 65 % against 70 to 80 % for tuples, a gap with a standard error of about 0.15, hence 72 and not more. *Line 9 (80 %):* to answer from a hex word the model must find the column's index, take the right hex digit, turn it into four bits and read one; I do not think a 7B model does this, and expect it to answer by habit (mostly yes), which on balanced questions is 0.50; with 20 questions even a true 0.50 reads above 0.60 about one time in seven. *Line 10 (80 %):* with no reading the model will name a handful of services, about half of them wrong, which is below a list of everything (0.83); it is not 95 because a model that lists nearly all services whenever it is lost would sit exactly on the baseline, and "below" is strict. *Line 11 (60 %):* the existence half I give about 85 %, the F1 half about 65 % (tuples' own F1 on a dense graph may be only about 0.6 to 0.7, because the model drops items), and they are correlated. *Line 12 (65 %):* adjacency has both directions on one line; the rivals are tuples (more detail, which can help and can distract) and the matrix forms (small, hard to read). *Line 13 (75 %):* the sparse graph is easy for tuples (1,800 tokens) and the matrix needs counting; with 12 existence questions the noise is large (0.14 per format), hence 75. *Line 14 (80 %):* on a sparse graph a list is short (about 6) and the adjacency line gives it at once.

What each outcome would mean, written now so that I do not read it afterwards to suit the numbers. *Lines 4 and 5 yes:* the efficiency half of the text is real, as arithmetic: about a sixth of the tokens for the packed form on a dense graph. *Line 5 NO:* something about the tokenizer is not as I think; the counts of the run say what. *Lines 9 and 11 yes:* a stock model cannot read the 64-bit packing; the saving exists on the page but is not available to the model, so a cut-over would need either a model trained on the format or a host that answers the question from the bitset itself and hands the model only the answer or the slice it asked for, which is the way a host/model split already works in the repository (the gate decides, the model proposes). That is not a finding against the bitset on the host side. *Line 9 NO:* the model reads the packed form better than I expect, and the next question is whether it holds when the graph grows past 64 services, where the one-word-per-row packing of the text no longer fits a row in one integer. *Lines 6, 7 and 12 yes:* what the model reads best is not the smallest form but the one that puts the answer on one line (adjacency), a lever that costs a host a few lines of code and fewer tokens than the tuples (0.85 of them); so the cut-over the text describes is the wrong axis: the right one is "which direction is the question about", not density. *Line 3 NO:* the model cannot read even the plain text of a dense graph (the 'attention confusion' of the text would be real for tuples); then lines 6 to 14 compare formats on a model that reads none of them, and I will say so. *Lines 13 and 14:* the contrast on a sparse graph, where the packing should buy nothing; a NO on 13 would say that the matrix forms are not worse even there.

## Reading rules (fixed now; the printout prints exactly these)
The fourteen lines above are the reading rules; `kv_dense.verdict_dense` computes them from the saved result. Thresholds: existence floor 0.60, matrix tokens 0.35, bitset tokens 0.20, in-recall gain 0.15, out over in 0.10, matrix below 0.05, bitset chance 0.60, bitset below 0.10 (`N_EXIST_MIN`, `N_TOK_MATRIX`, `N_TOK_BITSET`, `N_IN_GAIN`, `N_OUT_OVER_IN`, `N_MATRIX_BELOW`, `N_BITSET_CHANCE`, `N_BITSET_BELOW`). A list question's answer is the set of `(r,c)` it contains; a yes/no answer is the first "yes" or "no" word of the reply; a reply with neither counts as wrong and is also counted as "no answer". "Mean F1" is the mean over the list questions (the out and in questions together) of the F1 of each. "Recall on the in questions" is the mean recall over those questions only. The token count of a format is the mean over the graphs of the tokenizer's count of the state alone. Ties go to "yes" where the line says "at least", "at most" or "highest" (a tie for the highest F1 counts), and to "NO" where it says "below" or "above".

## What this cannot show
A reading test of one model: a 7B at 4 bits, greedy, one phrasing of the instruction, one order of columns and of bits, a state that comes first and a question after it. A different prompt, a larger model, a model that is given a worked example of the packing, or one that may call a tool to decode it could all do better. The sample is small (64 questions per format; a standard error of 0.06 to 0.1 on a share), eight graphs, one seed, so a gap of a few points is not a finding; the lines are set at gaps of 0.05 to 0.15 and I will say which came out close. Reading is not writing: a model could read a bitset badly and still propose an edit that a host checks. Nothing here touches the claim about 10,000 agents (item 100), nor the claim of a snap onto a lattice, which is not tested.

## Related work (from memory, not searched; check before citing)
That the way a graph is put into text changes what a language model can answer is shown by Fatemi, Halcrow and Perozzi, "Talk like a graph: encoding graphs for large language models" (2023), and by the NLGraph benchmark of Wang et al., "Can language models solve graph problems in natural language?" (NeurIPS 2023); I remember that both find large differences between encodings and between graph tasks. I do not remember either testing a packed-integer form. If I remember correctly, the finding that the encoding matters would not be new; what would be new here is the packed form, and the baseline of answering with everything, which I add because dense graphs make it strong.

## How it is run
In its own Colab notebook, `python/colab/axi_dense_test.ipynb` (a separate one, so that the notebook of the layout and block tests is untouched): Cells 1 to 5 as in the earlier notebooks (GPU, upload `axi-colab-tensor.zip`, install, Drive, load the model), Cell 6 a safety check without model time (the prompts against the tokenizer's own chat template, every state read back to its edges, the real token counts), Cell 7 a quick look at one dense graph in two formats, Cell 8 the run: the 40 (graph, format) pairs in order, one line per pair written to a file, so a dropped session carries on where it stopped. About 320 prompts of 1,000 to 5,000 tokens (a prompt is read afresh each time, no cache is kept), a few answers of up to 160 tokens: tens of minutes on a T4. It prints the table and the fourteen lines and saves `axi_dense.json`; send that file back and this page gets a "Result" section without changing anything above this line.
